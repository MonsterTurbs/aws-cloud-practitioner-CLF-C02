🧩 Big picture: After you deploy, you must manage

Creating infrastructure (VPCs, EC2, ECS, databases, etc.) is step one. In real environments, you also need to:

  • 🧰 Manage workloads at scale (servers, patching, automation)
  • 📦 Standardize deployments so teams don’t build 10 different versions of the same thing
  • 🔁 Share resources across accounts (e.g., one centrally-managed VPC used by many teams)
  • 🧾 Enforce configuration rules (avoid “drift” from company policies)
  • 🔐 Stay compliant with licensing (don’t exceed purchased software licenses)
✅ Key idea: Cloud management is about repeatability (templates), visibility (who changed what), and control (policies, guardrails).

🛠️ Systems Manager (SSM): Central management of workloads

AWS Systems Manager helps manage fleets of servers (usually EC2, but can also include on‑prem servers if they run the SSM Agent). It’s a “central control panel” for operations.

🧑‍💻 What SSM is good for

  • 🧩 Fleet management: manage many servers from one place
  • 🩹 Patch orchestration: roll out updates/patches across multiple servers
  • 🔧 Automation: run repeatable operational tasks (runbooks)
  • 🧾 App configuration: distribute config values via Parameter Store and AppConfig

🔑 Two exam-friendly SSM features

1) Parameter Store 🧷

  • Central place to store configuration values (like URLs, feature flags, environment names).
  • Apps fetch the value when needed (via SDK/CLI/API).
  • Helps avoid “hard-coding” values into source code.

2) AppConfig 🚦

  • Builds on the idea of Parameter Store but focuses on controlled config deployments.
  • Lets you roll out new config versions safely (e.g., staged rollout) and roll back if needed.
⚠️ Practical mental model:
  • Parameter Store = “my app asks for config” (pull model) 🙂
  • AppConfig = “I manage config releases” (controlled rollout) 😌

🧪 Example: Avoid hard-coded endpoints

Imagine you have a frontend that calls an API. Instead of hard-coding https://api.company.com/v1 inside the app:

  • Store it as a parameter: /prod/api/baseUrl → https://api.company.com/v1
  • If the API URL changes, update it once in Parameter Store.
  • All apps pulling that value will use the new URL (after refresh / next fetch).
✅ Exam wording you may see: “central place for application configuration values” → often points to SSM Parameter Store (or Secrets Manager if it’s sensitive like passwords/keys).

📦 Standardizing cloud resources for teams

In growing organizations, manual creation becomes error-prone and inconsistent. AWS provides services so teams can use standard patterns instead of inventing their own each time.

Service What it provides Simple way to remember
Service Catalog 🗂️ Predefined “products” (templates) users can deploy with limited choices. “Company-approved templates” ✅
Proton 🧪 Standard templates focused on serverless / container environments & deployments. “Standard platform for apps” 🚀
CloudFormation 🧱 Infrastructure as Code (templates that define resources and configs). “Infrastructure recipe in code” 📜
RAM 🔗 Share the actual resource across accounts (not a template). “Share the real thing” 🤝
⚠️ Don’t mix up:
  • Service Catalog/Proton = share blueprints/templates 🧩
  • RAM = share the actual created resource 🔗

🔗 AWS Resource Access Manager (RAM): Share resources across accounts

By default, resources like a VPC are tied to the account that created them. RAM enables controlled sharing of certain resources to other accounts (often within an AWS Organization).

📌 Why RAM exists

  • 🏢 One team manages networking centrally (e.g., a shared VPC).
  • 👥 Other teams deploy workloads into that shared network from their own accounts.
  • 🧭 Reduces duplicated VPCs and inconsistent network configurations.

🧪 Example scenario

You have multiple AWS accounts: Networking, Dev, and Prod.

  • Networking team creates a VPC once in Networking.
  • They share the VPC via RAM to Dev and Prod.
  • Dev/Prod teams deploy their compute services “into” the shared VPC.
✅ Exam clue: If the question says “share a VPC (or other resource) across multiple accounts” → think Resource Access Manager (RAM).

🧾 AWS Config: Configuration tracking + compliance rules

Even if you start with CloudFormation templates, people can still change settings after deployment. AWS Config helps you detect and evaluate configuration changes over time.

👀 What AWS Config does

  • 🕵️ Tracks resource configuration changes (who/what changed, and when).
  • 📏 Lets you define rules (desired configurations).
  • 🚨 Shows violations when resources drift away from required settings.
  • 🏢 Can work across multiple accounts (especially with Organizations).

🧠 Beginner-friendly mental model

Think of AWS Config as a policy checker and change history tool.

  • “Is this resource configured correctly?” ✅/❌
  • “What changed since last week?” 🗓️

🧪 Example rule

Company policy: “S3 buckets must not be public.”

  • AWS Config rule checks buckets for public access settings.
  • If someone makes a bucket public, Config flags it as non-compliant.
  • Ops/security team can then fix the settings to match the policy.
⚠️ Useful exam phrasing: “enforce configuration rules,” “detect configuration drift,” “audit configuration changes” → AWS Config.

📜 AWS License Manager: Stay compliant with software licensing

Larger organizations may run licensed software on cloud compute (e.g., database software on EC2). You must ensure usage does not exceed purchased licenses.

✅ What License Manager helps with

  • 🧾 Define rules that reflect your license agreements.
  • 🔔 Get alerts/warnings when usage risks violating those rules.
  • 📈 Gain visibility into license consumption across your environment.
✅ Exam clue: “track software licenses / avoid exceeding license limits” → AWS License Manager.

📝 Exam tips + quick checks

⚡ One-line recall (fast)

  • 🛠️ Systems Manager = manage servers + operations + app config (Parameter Store/AppConfig)
  • 🗂️ Service Catalog = deploy company-approved templates (“products”)
  • 🧪 Proton = standardized serverless/container environments for teams
  • 🔗 RAM = share actual AWS resources (e.g., a shared VPC) across accounts
  • 🧾 AWS Config = configuration history + compliance rules + drift detection
  • 📜 License Manager = stay within software license limits

✅ Quick check questions (self-test)

  1. Your networking team created one VPC and wants all other accounts to use it. What service helps?
    Answer: Resource Access Manager (RAM) 🔗
  2. You want to detect when someone makes an S3 bucket public against policy. What service helps?
    Answer: AWS Config 🧾
  3. You want a central place for non-secret config values like API base URLs.
    Answer: Systems Manager Parameter Store 🧷
  4. You want to manage and roll out configuration changes safely (with the option to roll back).
    Answer: Systems Manager AppConfig 🚦
  5. You want to ensure you don’t exceed purchased database software licenses running on EC2.
    Answer: AWS License Manager 📜
🎯 Strategy tip: In CLF-C02 questions, identify the goal first:
  • Sharing a resource across accounts → RAM
  • Checking configuration compliance/drift → AWS Config
  • Central operations & app configuration → Systems Manager
