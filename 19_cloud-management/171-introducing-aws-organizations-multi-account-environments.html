🏢 AWS Organizations & Multi‑Account Environments — Study Guide

CLF‑C02 reviewer: why companies use multiple AWS accounts, and how AWS Organizations helps manage them centrally.

🎯 What you should learn from this lecture

  • Why a company might use multiple AWS accounts instead of (or in addition to) many IAM users in one account.
  • How AWS Organizations lets you manage many accounts as one company setup (billing + governance).
  • What Organizational Units (OUs) are used for (grouping accounts logically).
  • What Service Control Policies (SCPs) do (permission guardrails across accounts).

🧩 The idea: one account vs multiple accounts

So far, a simple setup looks like this: 1 AWS account + many IAM users. That can work, especially for small teams.

But as a company grows, it often becomes cleaner to split into multiple AWS accounts (e.g., one account per team or environment), while still managing them together.

📌 Beginner tip: Think of an AWS account as a security + billing boundary. Splitting accounts can reduce confusion and reduce blast radius.

✅ Why use multiple AWS accounts?

1) 🧱 Service limits apply per account

Many AWS limits (quotas) are account-based. Example mentioned: the number of Elastic IPs you can allocate. With multiple accounts, you effectively get those limits per account.

Note: Often you can request a quota increase via AWS Support, so limits should not be the only reason.

2) 🆓 Free tier / free usage can apply per account

Some free-tier or monthly free usage amounts can be utilized across accounts. The lecture highlights that this is not “gaming the system” — AWS is aware of this and it’s an accepted approach.

3) 🧭 Organization & separation of workloads/teams

In larger companies, multiple teams may build different apps. In one giant account, it can become hard to answer questions like:

  • “Who owns this S3 bucket?”
  • “Which team created these resources?”
  • “Is this for testing or production?”

With multiple accounts, you can separate by team, environment (dev/test/prod), or project.

⚠️ Important: Multiple accounts can reduce “mess,” but they also add management complexity. That’s exactly why AWS Organizations exists.

🏛️ AWS Organizations: manage many accounts like one company

AWS Organizations groups multiple AWS accounts into one structure so you can manage them centrally. Key benefits mentioned in the lecture:

  • 🧾 Centralized billing (one consolidated bill instead of many)
  • 🧠 Better visibility and easier management across accounts
  • 🛡️ Ability to apply organization-wide governance and security

🧠 Mental model: Organizations is the “company” layer above individual AWS accounts.

🗂️ Organizational Units (OUs)

Within AWS Organizations, you can group accounts into Organizational Units. This helps you apply policies and manage accounts by purpose.

🧪 Example OU setup (common real-world pattern)

One company, multiple accounts, grouped by environment:

OU: Production OU: Development OU: Testing OU: Shared Services

Then you place accounts under each OU, for example:

  • Prod Account for live customer workloads
  • Dev Account for feature work and experiments
  • Test/Staging Account for pre-release validation

🧾 Centralized billing + shared management

Organizations can consolidate billing so your finance team gets a unified view. This is especially useful if you have “dozens of accounts,” where separate bills become difficult to manage.

🧰 Organization-aware services (example: AWS Backup)

Some AWS services integrate directly with Organizations so you can manage them across accounts. The lecture example: AWS Backup.

  • Instead of configuring backup plans in every account manually… 😵
  • …you can enable Organizations support and manage backup policies across accounts from one place. ✅

The set of services supporting Organizations is continuously growing.

🔎 Key terms (must-know)

  • AWS Account — boundary for billing, resources, and security administration.
  • IAM Users — identities within an account (users/roles/policies) to access resources.
  • AWS Organizations — service to group and centrally manage multiple accounts.
  • OU (Organizational Unit) — folder-like grouping of accounts inside an Organization.
  • Consolidated Billing — single bill for multiple accounts.
  • SCP (Service Control Policy) — organization-wide permission guardrails (maximum permissions).

🛡️ Service Control Policies (SCPs): guardrails across accounts

A Service Control Policy (SCP) lets you define a maximum set of permissions for accounts (or OUs). Think of it as a “permission ceiling.”

✅ What SCPs do: They can prevent accounts from granting permissions beyond what the SCP allows.

🚫 What SCPs don’t do: They don’t automatically grant permissions to users. IAM policies are still needed inside each account.

🧠 Simple example

Imagine you want to ensure that no one in the Development OU can use a costly service. You could apply an SCP that denies that service. Even if someone tries to attach an IAM policy allowing it, the SCP still blocks it.

⚠️ Exam trap to avoid: “SCPs grant permissions.” No — SCPs mainly limit what’s possible. IAM policies still control what is actually allowed for identities.

🧾 Mini-summary (high-yield)

  • 🏗️ Multiple accounts help with separation (teams/environments) and can provide separate service limits and sometimes free usage.
  • 🏛️ AWS Organizations groups accounts for central billing and centralized management/governance.
  • 🗂️ OUs are used to organize accounts and apply policies logically.
  • 🛡️ SCPs set guardrails (maximum permissions) across accounts/OUs.
