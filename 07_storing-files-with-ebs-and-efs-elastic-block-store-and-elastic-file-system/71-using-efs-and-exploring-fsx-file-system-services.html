Using EFS & Exploring FSx (File System Services)

Reviewer / Study Guide (Beginner-Friendly) — AWS CLF-C02

📦 Topic: File Storage 🧠 Focus: EFS, FSx (Lustre) 🧩 Link: EC2 + VPC 🖨️ A4 Print-Ready

1) Big Picture: Where EFS Fits

Elastic File System (EFS) is a managed, scalable network file system. Unlike EBS (a virtual hard drive attached to EC2), EFS is a shared file system that can be reached by multiple compute services. 🙂

✅ Key mindset

  • EBS = “Attach a disk to an EC2 server” (block storage). 💽
  • EFS = “Attach/mount a shared file system” (network file system). 📁
  • S3 = “Store objects/files without a file system” (object storage). 🪣

2) Where You Configure EFS

Option A: Attach/Create from the EC2 Launch Wizard 🧙‍♂️

When launching an EC2 instance, the default storage is typically EBS. But you can also add a file system (EFS / FSx) during storage configuration.

  • ⚠️ You usually must pick a Subnet first, because EFS is created/used within a VPC and is associated with subnets.
  • 📌 You may see both EFS and FSx as choices (FSx is also a file system, but aimed at specific performance needs).

Option B: Use the dedicated EFS service console 🧭

EFS has its own service dashboard (not inside the EC2 dashboard), because EFS is not an EC2-only service.

  • 🌍 Regional service: Your selected AWS region matters.
  • 🕸️ VPC matters: You choose which VPC in that region the file system belongs to.

3) Creating an EFS File System: What You Decide

When you create an EFS file system, you configure network placement, access controls, and some performance-related choices. You generally do not pick a fixed size like you do with disks. 😌

Configuration Area What it means (beginner-friendly)
Region + VPC 🌍🕸️ EFS is created in a specific region and connected to a specific VPC. Your compute resources must be able to reach that VPC network.
Subnets covered 🧩 You decide which subnets should be able to reach the file system. If an EC2 instance runs in a subnet that isn’t covered, it won’t be able to access EFS.
Performance / workload optimization ⚡ You can choose settings optimized for certain patterns (e.g., more throughput for large files or high read/write operations). Exact tuning is more advanced than CLF-C02, but know it exists.
Automatic scaling 📈 You typically don’t set a “disk size.” EFS is designed to scale as files grow (you pay for what you use). This flexibility can be more expensive than simpler storage choices.
Encryption 🔐 You can enable encryption so stored files are protected. You can also control how encryption is handled (details vary by configuration).
Security Groups 🛡️ EFS is a network-reachable resource, so it uses security groups to control which traffic can reach it—similar in spirit to how instances use security groups.
Access policy ✅🚫 You can define rules that control what can be written/read, adding an extra layer of access control beyond the network rules.

🧠 Exam-friendly takeaway

  • EFS is a managed network file system that can be shared and is not EC2-only.
  • EFS is tied to Region + VPC, and access is controlled by subnets + security groups.
  • You generally don’t pre-size it like a disk; it is designed to scale automatically.

4) Simple Example Scenarios (Mental Models)

Scenario 1: Shared uploads for multiple EC2 web servers 🌐📸

You run 2+ EC2 instances behind a load balancer. Users upload images. If each instance stores files locally, users might not see uploads consistently.

Better: Mount a shared file system so all web servers see the same files.

Think: “All servers read/write the same folder.”

Scenario 2: Need a file system, not a disk 🧠

You don’t want to manage formatting/mounting disks and resizing volumes. You want a file system that grows as needed.

EFS fits because you focus on folders/files, not disk administration.

5) FSx (Lustre) — When EFS Isn’t Enough

FSx is another AWS file system family. One notable option is FSx for Lustre, which is designed for high-performance file access workloads. 🚀

⚖️ Practical positioning

  • EFS is typically the default choice when you need a shared file system in AWS. 🙂
  • FSx Lustre can be preferable for certain high-performance, file-based workloads where EFS may not meet performance needs. 🏎️
  • They are not “feature-equal” — FSx Lustre works differently and can have limitations compared to EFS.
Feature EFS FSx for Lustre
Main goal General-purpose shared file system High-performance file access workloads
Default choice? Usually yes ✅ Only for specific needs ⚠️
How to think about it “Shared folders for apps/services” “Performance-oriented file system for heavy workloads”

Note: For CLF-C02, you typically only need to recognize what FSx is and why it might be chosen (specialized, high-performance file access), not the deep configuration steps.

6) Quick Recap Checklist (What to Remember)

  • 📌 EFS is a dedicated service (not inside EC2) because it’s not EC2-only.
  • 🕸️ EFS lives in a Region and is connected to a VPC; access depends on subnets and security groups.
  • 📈 EFS focuses on automatic scaling; you don’t typically choose a fixed capacity upfront like with a disk.
  • 🔐 You can enable encryption and define access policies for stronger security.
  • 🏎️ FSx (Lustre) is a specialized option for certain high-performance file-based workloads.
