Scaling & Load Balancing — Module Summary (Reviewer)

📌 Topic: Elasticity, Scalability, High Availability 🧠 Focus: EC2 Auto Scaling + Elastic Load Balancing 📝 Goal: Understand the “why” + exam vocabulary

1) Core idea of this section 🌍

This section explains how AWS helps you handle changing workload requirements (traffic spikes) using Auto Scaling and Load Balancing.

Why it matters (business impact) 💼
  • 📉 Too little capacity → slow app or crash → lost users / lost revenue.
  • 📈 Too much capacity → you pay for idle servers → wasted cost.

2) Key terms you must remember 🧠

  • ⚡ Elasticity: ability to scale instantly when needed (up and down).
  • 📈 Scalability: ability to grow capacity in general (handle more load).
  • 🛡️ High availability: staying online by avoiding single points of failure and spreading workload.

Beginner example 🧩

A web app has normal traffic most days, but spikes during a sale. AWS lets you add instances during spikes and remove them after. You get performance when you need it and avoid paying too much when you don’t.

3) Two core AWS capabilities in this topic 🧱🧱

🔁 EC2 Auto Scaling

Automatically adds/removes EC2 instances based on rules you set. It helps keep the right capacity without over-provisioning.

⚖️ Elastic Load Balancing (ELB)

Distributes incoming traffic across instances so the workload is shared and no single instance gets overwhelmed.

Mental model 🧠
  • Auto Scaling decides: “How many servers do we need?”
  • Load Balancer decides: “Which server gets this request?”

4) EC2 Auto Scaling — must-know details 🔁

Capacity settings

  • 🎯 Desired capacity: default number of instances you want running.
  • 🧱 Minimum: never go below this.
  • 🚀 Maximum: never go above this.

Launch Template / Launch Configuration 🧾

Auto Scaling must know what kind of instances to launch. That configuration is stored in a Launch Template.

  • 📀 AMI (OS + base software)
  • 🖥️ Instance type
  • 🌐 VPC + subnets (where instances will be placed)
  • 🧱 Security groups (instance firewall rules)

Scaling triggers (rules) 📏

Auto Scaling changes instance count based on metrics (commonly average CPU utilization). You define the thresholds. 

Example (conceptual):
- If average CPU > 50%  -> scale out (add instances)
- If average CPU < 20%  -> scale in  (remove instances)
Key takeaway ✅

You keep control over the instance type/AMI/VPC/subnets, but AWS launches (and removes) instances automatically.

5) Elastic Load Balancing — must-know details ⚖️

Scaling is not enough by itself. If you have multiple instances, you also need traffic distributed evenly. That is what the Elastic Load Balancer service provides.

Two main load balancers (for this level) 🧭

🌐 ALB — Application Load Balancer

  • Best default for websites / HTTP(S).
  • More features for routing (path/cookie/rules).
  • Can do SSL termination (handles HTTPS, forwards traffic internally).

🧵 NLB — Network Load Balancer

  • Great for non-HTTP network traffic.
  • Can offer strong performance in certain cases.
  • Provides a fixed IP (useful in some scenarios).
Plain-English SSL termination 🔒

Your users send HTTPS to the Load Balancer. The Load Balancer decrypts it, then forwards requests inside AWS. Your EC2 app does not need to manage certificates on every instance.

Target Groups 🎯

A Target Group is the group of instances that can receive traffic. Target groups are connected to your VPC and subnets.

  • 🔗 If the Load Balancer is connected to an Auto Scaling Group, instances launched by Auto Scaling are added automatically to the target group.
  • 🩺 Health checks ensure traffic is only routed to healthy instances.
Important detail from the lecture 🧠

Load balancer rules (how requests are forwarded) are typically configured after the load balancer is created.

  • Target Group: the pool of instances where the load balancer forwards requests.
