Creating Load Balancers + Combining Them with Auto Scaling

🧭 Quick Review (what you must understand)

  • Load Balancer distributes incoming traffic across instances so no single server gets overwhelmed. ⚖️
  • Target Group is the set of instances the Load Balancer forwards requests to. 🎯
  • Health Checks decide if an instance is “healthy” and should receive traffic. ❤️‍🩹
  • Auto Scaling Group automatically adds/removes EC2 instances based on your rules/metrics. 📈📉
  • When combined: Auto Scaling adds instances → Load Balancer routes traffic to them automatically (via the Target Group). 🔁

🧱 Where can you create a Load Balancer?

You have two common entry points:

  • Inside the EC2 Auto Scaling “Create group” wizard — convenient when building everything together. 🧩
  • From the EC2 Dashboard → Load Balancers — create one first, then attach it later. 🛠️

Exam mindset: Auto Scaling = manages how many instances exist. Load Balancer = manages where traffic goes. Together they solve scale + distribution.

🌐 Choosing the Load Balancer type (basic)

For web servers (HTTP/HTTPS), you typically choose an Application Load Balancer (ALB). 🌍

  • ALB: best for HTTP/HTTPS traffic; can route based on URL paths, cookies, etc.
  • NLB: better for non-HTTP traffic or when you need a fixed IP (more advanced).

For CLF-C02, it’s usually enough to know: ALB = web traffic, NLB = network-level / other protocols.

🏷️ Internet-facing vs Internal

When you create a Load Balancer, you pick whether it is:

  • Internet-facing 🌍 — accepts requests from the public internet (common for websites).
  • Internal 🏢 — only reachable inside your VPC (common for private services, internal APIs, etc.).

Beginner example:

  • Your public website → internet-facing ALB → forwards to EC2 instances in public subnets.
  • Your private database/admin tool → internal LB → only your internal network can reach it.

🗺️ VPC + Subnets must match (important)

When combining a Load Balancer with an Auto Scaling Group:

  • The Load Balancer must be created in the same VPC as the instances. ✅
  • The Load Balancer must use subnets that can reach those instances (usually the same subnets you allow Auto Scaling to launch into). ✅

Simple rule: If the Load Balancer can’t “see” the instances (wrong VPC/subnets), it can’t forward traffic. 🚫

👂 Listener rules (what traffic does the LB accept?)

You define what the Load Balancer “listens” to. For a typical web app:

  • HTTP (port 80) for unencrypted web traffic
  • HTTPS (port 443) for encrypted traffic

In the lecture, the example uses HTTP as the listener.

🎯 Target Groups (where requests are forwarded)

A Target Group is basically a named collection of targets (often EC2 instances) that can receive traffic from the Load Balancer.

How it works with Auto Scaling 🔁

  • You create/choose a target group for the Load Balancer.
  • If the Load Balancer is attached to an Auto Scaling Group, instances launched by Auto Scaling are automatically added to that target group. ✅
  • This means you don’t manually maintain the list of servers.
LB (internet-facing)  →  Target Group  →  EC2 instances created by Auto Scaling

❤️ Health Checks (keep traffic away from broken instances)

Health checks are how AWS decides whether a target (instance) should receive requests.

  • If an instance fails health checks, the Load Balancer can stop routing traffic to it. 🚑
  • Auto Scaling can also replace unhealthy instances (depending on your configuration). 🔄

Beginner example: If your web server process crashes on one instance, health checks fail → the Load Balancer avoids it → users still get served by the healthy instances.

📏 Auto Scaling capacities (Desired / Min / Max)

These settings define the size boundaries of your Auto Scaling Group:

  • Desired capacity 🎯 — the “normal/default” number of instances you want running.
  • Minimum capacity 🧱 — you never go below this number.
  • Maximum capacity سقف — you never go above this number (prevents runaway costs).

Example: Desired = 1, Min = 1, Max = 4 → you always have at least one instance, and you can scale up to 4 if needed.

📈 Scaling policies (WHEN do we add/remove instances?)

You typically define scaling based on metrics. A common one is Average CPU Utilization.

Beginner-friendly example 🤓

  • If average CPU across instances goes above 50% → scale out (add instances).
  • If average CPU goes below the target → scale in (remove instances).
IF avg CPU > 50%  → add instances (scale out)
IF avg CPU drops   → remove instances (scale in)

This gives elasticity: you adapt to traffic without permanently paying for peak capacity.

🔔 Notifications + 🏷️ Tags

  • Notifications: you can send emails (or other alerts) when instances scale up/down, so you know what’s changing. 📬
  • Tags: label resources for organization and cost tracking (e.g., Project=Demo, Env=Dev). 🏷️

🧪 Mini “Step-by-step” summary (from the lecture)

  1. Create/choose an Auto Scaling Group and a Launch Template (how instances should be configured).
  2. Create/attach a Load Balancer (usually ALB for web apps).
  3. Choose VPC + subnets (must align so the LB can reach instances).
  4. Configure Listener (e.g., HTTP).
  5. Create/choose Target Group (Auto Scaling will auto-register instances).
  6. Configure Health Checks (detect broken instances).
  7. Set Desired / Min / Max capacity.
  8. Add Scaling Policies (e.g., CPU threshold).
  9. (Optional) Add notifications and tags.

📝 Quick self-test (CLF-C02 style)

  • Q: What automatically distributes traffic across multiple EC2 instances? ✅ Load Balancer
  • Q: What automatically adds/removes EC2 instances based on demand? ✅ EC2 Auto Scaling
  • Q: What groups the instances that receive traffic from a Load Balancer? ✅ Target Group
  • Q: What helps avoid routing traffic to crashed instances? ✅ Health Checks

✅ Final takeaway

Core idea: Auto Scaling ensures you have the right number of instances. Load Balancing ensures traffic is routed to the right instances (and only healthy ones). Together, you get scalability + availability + cost control.

This is the level of understanding typically expected for Cloud Practitioner. Implementation details are deeper-level exams.
