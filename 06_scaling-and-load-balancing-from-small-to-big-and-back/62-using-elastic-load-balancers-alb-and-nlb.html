1) What is a Load Balancer? ⚖️

A load balancer is a service that sits in front of your servers (often EC2 instances) and distributes incoming traffic across them so that:

  • ✅ No single server gets overwhelmed
  • ✅ Your app stays available even during traffic spikes
  • ✅ You can scale out (add instances) and still serve users smoothly
Memory hook 🧩

Think of a load balancer like a traffic enforcer in a busy mall entrance: it directs people to multiple counters so lines stay short.

2) AWS “Main” Load Balancers in this section 🏗️

AWS commonly highlights two load balancers for EC2 traffic distribution:

  • Application Load Balancer (ALB) — usually the default choice for web apps (HTTP/HTTPS).
  • Network Load Balancer (NLB) — leaner, great for non-HTTP traffic and when you need a static IP.

3) Quick Comparison Table: ALB vs NLB 🧾

Main traffic type 🌐 Best for HTTP / HTTPS 🔌 Best for non-HTTP (general network traffic)

SSL/TLS termination ✅ Yes — commonly used for this ✅ Possible as well

4) Application Load Balancer (ALB) — What to remember 🌐

ALB is feature-rich and is usually your best option for a typical web application.

Key capabilities ✅

  • 🔎 Understands HTTP: it can inspect requests and make decisions based on details like:
    • 🍪 Cookies
    • 🧭 URL path (e.g., /api vs /images)
    • 🏷️ Hostname rules (e.g., app.example.com vs admin.example.com)
  • 🧩 Can reduce application complexity: the load balancer can handle routing logic so your app servers stay simpler.
  • 🔐 Supports SSL/TLS termination (see next section).
Beginner example 🧪

You have two EC2 instances:

  • Instance A handles /api requests
  • Instance B handles /images requests

An ALB can route incoming requests to the correct instance based on the URL path.

5) What is “SSL Termination”? 🔐

SSL/TLS termination means the load balancer becomes the endpoint for encrypted HTTPS traffic:

  • 👤 User sends encrypted HTTPS request to the Load Balancer
  • 🔓 Load Balancer decrypts it (using the certificate)
  • ➡️ Load Balancer forwards the request to your EC2 instance inside AWS (often as plain HTTP)

This is typically fine because the traffic from the load balancer to your instances stays within AWS networking boundaries.

Why this is useful 🎯

Your EC2 instances (web servers) don’t need to manage certificates and encryption details. The load balancer does it for them, simplifying your servers.

6) Network Load Balancer (NLB) — What to remember 🔌

NLB is leaner and often chosen for:

  • ⚡ Performance-focused needs (less overhead, fewer features)
  • 🧱 Non-HTTP traffic (not web requests)
  • 📌 Scenarios where you must have a fixed IP
Beginner example 🧪

You’re not running a website. Instead, you have a custom service receiving non-HTTP traffic. You still want to distribute load across multiple EC2 instances. In that case, an NLB can be a better fit.

7) Fixed IP: Why it matters (sometimes) 📌

One highlighted difference is that NLB provides a fixed IP address. That can matter for systems that require allow-listing a stable IP.

Note: For many website use cases, you’ll often use a domain name pointing to the load balancer, so the lack of a fixed IP on ALB is usually not a problem.

8) Exam-focused takeaways 📝

  • ✅ ALB = default for web apps (HTTP/HTTPS), richer features, smart routing rules.
  • ✅ NLB = leaner, great for non-HTTP traffic and can provide a static IP.
  • ✅ SSL termination = load balancer handles HTTPS decryption so your instances can be simpler.
Fast recall ⚡

ALB = “Application/Web smart routing” 🌐
NLB = “Network-level + Fixed IP” 🔌📌
