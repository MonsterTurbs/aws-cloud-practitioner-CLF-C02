1) CloudWatch Console: What you do there

Idea: CloudWatch is your “monitoring command center” in AWS. You typically use it to:

  • 🧾 Inspect logs (grouped into log groups)
  • 📊 View metrics (CPU, errors, latency, etc.)
  • ⏰ Create alarms (notify or auto-act when metrics cross thresholds)
  • 🧩 Build dashboards (multiple charts in one page)

2) Logs in the console

🧾 Log Groups (think: folders)

In CloudWatch Logs, log entries are organized in Log Groups. A log group usually represents a workload or service. Example: a log group for an RDS instance, or for a Lambda function.

Beginner mental model: Log Group = container of related logs. Inside it, you’ll typically have streams/entries that come from specific instances/executions.

🔎 What you do with logs

  • Read what happened (errors, warnings, info)
  • Trace why a feature broke (e.g., “DB connection timeout”)
  • Confirm behavior (e.g., deployment version, request payload shape)

⚠️ Exam hint: Many services publish logs to CloudWatch. Example: Lambda writes logs to CloudWatch automatically (commonly tested concept).

3) Alarms in the console

Alarm formula: Metric + Statistic + Time Period + Threshold + Action

⏰ Step-by-step (based on the transcript)

  1. Select a metric (e.g., EC2 → per instance)
  2. Pick the statistic: average / sum / max (peak)
  3. Choose the time window (e.g., 5 minutes)
  4. Set a threshold (e.g., CPU > 80%)
  5. Define an action (e.g., send email via SNS)

“Average vs max” matters: max catches spikes; average can hide short spikes.

📧 Example: CPU utilization alarm

Scenario: You host a web server on EC2. If CPU is too high, users might feel slowness.

  • Metric: EC2 CPUUtilization
  • Statistic: Average over 5 minutes
  • Condition: > 80%
  • Action: Notify an email list using SNS 🔔

🧠 Remember: CloudWatch alarms don’t “send emails directly.” They usually trigger an action like SNS, which then delivers email/SMS/etc.

4) Metrics and Charts in the console

📊 Explore Metrics (by service)

CloudWatch lets you browse metrics by AWS service (e.g., EC2 metrics) and then drill down:

  • By Auto Scaling Group
  • By Instance
  • By other dimensions (depending on the service)

📈 Chart a metric over time

You can view a chart (e.g., last 3 days) and zoom/select a time range. This helps you answer questions like:

  • “Did CPU spike during deployment?”
  • “Is latency worse on weekends?”
  • “Is the problem constant or intermittent?”

Practical workflow: pick the right time range first, then interpret trends/spikes.

5) Dashboards in the console

Dashboards let you put multiple charts/widgets on one page so you can see the “health picture” fast. 🧩

🧩 Why dashboards are useful

  • Single-screen visibility for a workload (CPU, errors, latency, requests)
  • Quick checks during incidents (“Is it only one instance or all?”)
  • Compare different time periods easily (hours vs days)

🛠️ Auto vs custom dashboards

You can use dashboards created by AWS automatically (service-focused views) or create your own custom dashboard.

Best practice: build dashboards around user experience signals (errors/latency) + resource signals (CPU/memory).

6) Quick “Console Navigation” cheat sheet

  • 🧾 Logs → Find Log Groups → pick group → inspect log events
  • ⏰ Alarms → Create alarm → pick metric → set threshold → choose action (often SNS)
  • 📊 Metrics → pick service (EC2) → pick dimension (instance/ASG) → view chart
  • 🧩 Dashboards → use existing / create new → add widgets → choose time range

7) Self-test (CLF-C02 style)

Q1) What are the four main CloudWatch console areas discussed here?

Answer Logs (Log Groups), Alarms, Metrics/Charts, Dashboards.

Q2) When creating an alarm, what decision changes how spikes are handled: Average or Max?

Answer The chosen statistic. Max catches spikes; average can smooth them out.

Q3) If you want an email notification when CPU goes above 80%, what AWS service is commonly used with CloudWatch alarms?

Answer SNS (Simple Notification Service) is commonly used for notifications like email/SMS.

Q4) Why use dashboards instead of opening metrics one by one?

Answer Dashboards aggregate multiple charts/widgets on one page for quick visibility and faster troubleshooting.

⚠️ Common confusion: CloudWatch is primarily monitoring (metrics/logs/alarms/dashboards). It’s not the same as CloudTrail (API auditing) and not the same as AWS Config (resource configuration tracking).
