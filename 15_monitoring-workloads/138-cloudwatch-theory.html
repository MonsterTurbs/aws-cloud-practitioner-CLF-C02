☁️ CloudWatch (Theory) — Reviewer / Study Guide

Focus: What CloudWatch collects, how it helps you analyze data, and how alarms help you react early.

🎯 Learning Goals

  • Explain what Amazon CloudWatch is and why it matters for monitoring.
  • Differentiate logs vs metrics (and where they come from).
  • Describe how to collect extra data using the CloudWatch Agent or AWS APIs/SDK.
  • Understand how CloudWatch helps you analyze data (dashboards, insights) and act (alarms, forwarding).
🧠 One-liner to memorize CloudWatch = collect (logs + metrics) ➜ visualize (charts + dashboards) ➜ alert/act (alarms + integrations).

🔎 What is CloudWatch?

Amazon CloudWatch is AWS’s managed monitoring service. In simple terms, it helps you collect operational data (logs + metrics), analyze it, and react when something looks wrong.

📥 Collect

Logs (text events) and metrics (numbers over time).

📊 Analyze

Charts, dashboards, and log analytics to spot patterns and issues.

🔔 Act

Alarms and integrations (e.g., notify via SNS or trigger Auto Scaling).

📥 Collecting Data in CloudWatch

1) 🧾 Logs

Logs are event messages (often text) produced by your applications and services. Example: web server access logs, error logs, or “user X logged in” messages.

  • ✅ Some services write logs automatically (e.g., Lambda writes execution logs to CloudWatch).
  • 🔧 Other services (e.g., EC2 workloads) typically require configuration to send logs.
  • 🛠️ You can send logs from your code using AWS APIs/SDKs, or via tools/agents.
📌 Beginner tip Think of logs as a diary of events: useful for debugging and understanding “what happened and when.”

2) 📈 Metrics

Metrics are numbers collected over time (time-series). CloudWatch can show them as charts.

  • 🖥️ Example: EC2 CPU utilization, memory (when configured), network in/out.
  • 🪣 Example: S3 can publish storage-related metrics (e.g., bytes stored).
  • 🔁 Many AWS services publish standard metrics automatically (especially when logging/monitoring is enabled).
🧠 Log vs Metric (fast memory) Logs = “text story of events.” Metrics = “numbers that you graph.”

3) 🧰 Getting “Extra” Data (Agent + Custom Metrics)

If the default data isn’t enough, you can collect additional details.

  • 🔧 CloudWatch Agent: installable tool (commonly on EC2) to collect more detailed data and enable additional capabilities.
  • 🧩 Custom metrics: your application can publish its own measurements (e.g., “orders processed per minute”).
  • 🧑‍💻 AWS SDK / API calls: send arbitrary supported log/metric data to CloudWatch from your code.

🧪 Quick example (custom metric idea)

  • App tracks “CheckoutFailures” and sends it as a metric.
  • CloudWatch charts the failures per 5 minutes.
  • An alarm triggers if failures spike above a threshold.

📊 Analyzing Data

Collecting data is not enough—you need visibility. CloudWatch supports analysis via:

  • 📊 Metrics + Charts: visualize trends like CPU rising over time.
  • 🧩 Dashboards: a single page showing multiple charts (your “operations cockpit”).
  • 🔎 Log analytics features (e.g., log querying/insights) to search and summarize logs.
  • 🧭 Service-level visibility features (e.g., deeper views for certain workloads) to help troubleshoot faster.
📌 Practical use Dashboards are best for “Are we OK?” checks. Logs are best for “Why did this fail?” investigations.

🔔 Acting on Problems with Alarms

CloudWatch Alarms notify you (or trigger actions) when a metric goes outside the expected range. This is how you learn about issues early instead of discovering them from user complaints.

🧩 Alarm = Metric + Condition + Action

1) Select a metric 📈

Example: EC2 average CPU utilization over 5 minutes.

2) Define a condition ⚠️

Example: CPU > 80% for 5 minutes.

3) Choose an action 🔁

Example: notify via SNS, or trigger Auto Scaling.

🧪 Beginner-friendly examples

  • 🖥️ EC2 CPU alarm: If CPU > 80% → send notification (SNS) or scale out.
  • 🪣 S3 storage growth alarm: If bytes stored per day exceeds a threshold → notify team.
  • ⚙️ Lambda cost guard: If invocation count spikes unexpectedly → alert to investigate.
📌 Exam-style takeaway Alarms can both notify (via services like SNS) and trigger operational actions (e.g., Auto Scaling for EC2).

🧾 Quick Glossary

  • Logs 🧾 — detailed event records (usually text).
  • Metrics 📈 — numeric measurements over time (time-series).
  • Dashboard 📊 — collection of charts for at-a-glance health checks.
  • Alarm 🔔 — rule that watches a metric and triggers actions if thresholds are crossed.
  • CloudWatch Agent 🔧 — installed tool (commonly on EC2) to collect additional system/app data.

✅ Quick Check (with Answers)

  1. What are the two main data types CloudWatch works with?
    Logs 🧾 and metrics 📈.
  2. Why do we use dashboards?
    To get a fast overview of service/workload health using multiple charts in one place.
  3. How can you collect additional data from an EC2 instance?
    Install and configure the CloudWatch Agent (or publish via AWS SDK/API calls).
  4. What can a CloudWatch alarm do besides notifying you?
    Trigger actions such as Auto Scaling (and integrations through other services like SNS).

🧭 Mini Summary

CloudWatch is AWS’s core monitoring service: it collects logs and metrics (some automatically, others via agents/SDK), helps you analyze them through charts and dashboards, and lets you react quickly using alarms and integrations.
