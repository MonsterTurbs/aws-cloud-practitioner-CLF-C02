🎯 Why App Integration Services exist

When you have multiple applications (or microservices), they often need to communicate and share data. Building a custom HTTP API between every pair of apps can create extra work, extra cost, and tight coupling.

Core idea: AWS provides managed services that let apps exchange messages/events reliably — without each app needing to expose and maintain custom APIs.

In this course section, the 3 key services are:

  • 📦 SQS (Queue): apps pull messages when ready
  • 📣 SNS (Pub/Sub): messages are pushed to subscribers immediately
  • 🚌 EventBridge (Event bus): apps emit events; rules route events to targets

📦 SQS — Simple Queue Service

SQS is a queuing service. Application A sends messages to a queue, and Application B (or many apps) reads messages from that queue.

✅ Mental model

📮 Queue = inbox. Producers drop messages in. Consumers pick them up later.

⏳ Processing style

Asynchronous: sending a message does not mean it gets processed immediately.

🧩 How it works (simple flow)
App A (producer)  →  SQS Queue  →  App B (consumer)
                        ↑               |
                        |               | processes message
                        |               ↓
                     message stored   deletes/acknowledges

🧾 What is a “message”?

A message is just a data package (JSON, text, IDs, etc.). Example: {"site":"example.com","status":"crawled"}.

🧠 When SQS is a good fit

  • ✅ You want the receiver to process later (when it has time)
  • ✅ You want to buffer bursts of work (spikes in messages)
  • ✅ You want to decouple apps (producer doesn’t care when consumer runs)

Exam hint: If the scenario says “process later”, “decouple”, “queue”, “buffer”, “asynchronous” → think SQS ✅

📣 SNS — Simple Notification Service

SNS is a managed push messaging service (publish/subscribe). Apps publish a message to an SNS topic, and SNS immediately pushes it to all subscribers.

✅ Mental model

📢 Topic = announcement channel. Publish once, deliver to many subscribers.

⚡ Processing style

Synchronous-ish delivery: SNS forwards messages immediately to subscribers.

🧩 How it works (simple flow)
App A (publisher) → SNS Topic → App B (subscriber)
                               → App C (subscriber)
                               → ... (fan-out)

📱 Beginner analogy

Think of phone notifications: when someone sends a chat message, your phone gets a push notification right away 🙂 SNS can do this for apps too (and yes, SNS can also send to end-user devices).

🧠 When SNS is a good fit

  • ✅ You want to notify/trigger immediately
  • ✅ One message should reach multiple subscribers (fan-out)
  • ✅ You want a simple “publish message → subscribers react” flow

Exam hint: If the scenario says “notify multiple systems”, “push”, “fan-out”, “topic/subscribers” → think SNS ✅

🚌 EventBridge — Event Bus

EventBridge is an event bus service. Services and apps emit events, EventBridge receives them, and then triggers targets based on rules.

✅ Mental model

🧭 Event bus = central router. Events flow in; rules decide where they go.

🔁 Processing style

Immediate reaction: when a matching event occurs, EventBridge triggers actions right away.

🧩 How it works (simple flow)
App A emits event → EventBridge (rules) → triggers target (App B / AWS service)

Key nuance:
- App A reports/outputs an event.
- EventBridge routes it if rules match.
- App A does NOT need to know who is listening.

🧾 What counts as an “event”?

An event is a description of something that happened: “crawler finished”, “order placed”, “file uploaded”, etc. EventBridge can receive custom events from your code via AWS SDK.

🧠 When EventBridge is a good fit

  • ✅ You want event-driven architecture (apps emit events; others react)
  • ✅ You want the producer to be decoupled from consumers (producer doesn’t know targets)
  • ✅ You want routing rules ("if event type = X, send to Y")

Exam hint: If the scenario says “event bus”, “event-driven”, “rules route events to targets”, “producer doesn’t know consumers” → think EventBridge ✅

🧠 Choosing the right service

Use this quick decision guide (simple but exam-friendly):

📦 Choose SQS when…
  • Receiver should process later (asynchronous)
  • You want a queue/buffer for spikes
  • Consumers pull work when ready
📣 Choose SNS when…
  • You want to push notifications immediately
  • You want fan-out to multiple subscribers
  • You have a “publish once → many react” pattern
🚌 Choose EventBridge when…
  • You want event routing with rules
  • You want producer and consumers to be loosely coupled
  • You’re building event-driven workflows across apps/services

Key difference in one line:

  • 📦 SQS: store message in a queue; consumers pull later
  • 📣 SNS: publish message; SNS pushes to subscribers now
  • 🚌 EventBridge: emit event; rules route to targets (producer doesn’t care who listens)

🧪 One shared example: Crawler ➜ Processor

Imagine Application A crawls websites and Application B cleans/transforms the data. Here’s how each service would connect them:

📦 Using SQS (queue + pull)

  • App A drops a message: “Finished crawling site X”
  • App B pulls messages when it has capacity
  • Great when processing can happen later ⏳

📣 Using SNS (publish + push)

  • App A publishes: “Finished crawling site X”
  • SNS immediately pushes to App B (and also App C, App D if subscribed)
  • Great for immediate notification or fan-out ⚡

🚌 Using EventBridge (events + rules)

  • App A emits event: crawler.finished
  • EventBridge rule: “When crawler.finished, trigger App B”
  • App A doesn’t need to know App B exists (loose coupling) 🧩

✅ Quick Check (Exam-style Q&A)

Q1: You want to buffer work and let consumers process whenever they’re ready. Which service?

A: 📦 SQS (queue + asynchronous pull)

Q2: One app publishes an alert and multiple apps should receive it immediately. Which service?

A: 📣 SNS (topic + fan-out push)

Q3: You want apps to emit events, and you want routing rules to decide which targets get triggered. Which service?

A: 🚌 EventBridge (event bus + rules-based routing)

Memory tip: “Queue = SQS 📦, Notifications = SNS 📣, Event router = EventBridge 🚌” 🙂
