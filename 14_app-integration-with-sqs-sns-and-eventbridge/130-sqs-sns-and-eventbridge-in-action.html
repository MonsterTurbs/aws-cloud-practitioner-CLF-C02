🌍 Big Picture: Why “In Action” Helps

In the previous overview, these services can feel abstract. The console flow makes it concrete: you create something (queue / topic / rule), then you send an event/message, then another component receives it.

Key idea: You are connecting applications without building a custom HTTP API for every integration. 🙂

📥 SQS in Action: Queues

What you build: a queue that holds messages until a consumer reads and deletes them. 🧺

1) Create a Queue (Console mindset)

  • 🧾 Give the queue a name.
  • 🔀 Choose the queue type:
    • Standard: best throughput; messages can arrive out of order.
    • FIFO (First-In-First-Out): strict ordering; helps avoid duplicates and preserve sequence.
  • ⏳ Configure message behavior (how long messages live if not processed, visibility timeout, etc.).
  • 🔐 Permissions: who can send or receive messages.
  • 🔒 Optional: enable encryption.
  • 🧯 Optional: dead-letter handling for messages that fail processing repeatedly.

2) Send → Receive → Delete (The core loop)

Send (Producer) ✉️

In real apps, this is done via AWS SDK. In the console, you can “Send message” to test.

{
  "jobType": "crawl",
  "url": "https://example.com",
  "requestedAt": "2025-12-22T09:00:00+08:00"
}

Receive (Consumer) 👀

Consumers poll the queue and pull messages when ready.

Delete (Acknowledge) ✅

After processing, the consumer deletes the message to mark it as done.

Beginner rule: If you want “store and process later,” think SQS = Queue 🧺.

Common mistake: Receiving a message is not the same as completing it. You must delete it after successful processing.

📣 SNS in Action: Topics & Subscriptions

What you build: a topic that pushes messages to subscribers. 📢

1) Create a Topic

  • 🏷️ Give the topic a name.
  • 🔀 Choose ordering style (similar concept: FIFO vs standard).
  • 🔐 Configure access policies (who can publish / subscribe).
  • 🔒 Optional encryption.

2) Add Subscriptions (Who receives the push?)

SNS supports multiple subscriber types. Examples (from the lecture):

  • 📥 SQS queue (SNS pushes into a queue — good for buffering)
  • ⚙️ Lambda (invoke function when message arrives)
  • ✉️ Email (requires confirmation)
  • 📲 SMS
  • 🌐 HTTP/HTTPS endpoint

3) Publish a Message

You publish to the topic (usually from code via SDK). SNS immediately delivers to all subscribers. Think “one message → many recipients.” 🙂 

{
  "event": "crawl_finished",
  "url": "https://example.com",
  "status": "OK",
  "itemsFound": 128
}

Beginner rule: If you want “push to subscribers now,” think SNS = Notifications 📣.

Useful combo: SNS → SQS. SNS broadcasts; SQS buffers so consumers can process when ready. 🧠

🚌 EventBridge in Action: Rules & Targets

What you build: a rule that matches events, then triggers a target. 🧩

1) Create a Rule

  • 🏷️ Give the rule a name.
  • 🕒 Choose the rule type:
    • Scheduled: run on a schedule (e.g., every hour) ⏰
    • Event pattern: react to specific events (AWS service events or custom events) ⚡

2) Define the Event Source / Pattern

Example from the lecture: listen for S3 events. You can also produce and send custom events from your own applications.

Helpful mental model: EventBridge is an “event router.” It matches events → routes to targets. 🚌

3) Choose Targets (What should happen?)

After an event matches, you choose what to invoke. Common example: Lambda function ⚙️. 

{
  "source": "aws.s3",
  "detail-type": "Object Created",
  "detail": {
    "bucket": {"name": "my-bucket"},
    "object": {"key": "uploads/photo.jpg"}
  }
}

Beginner rule: If you want “react to events across services,” think EventBridge = Event Bus + Rules 🚌.

⚖️ Quick Comparison: SQS vs SNS vs EventBridge

📥 SQS — Queue (pull model)

  • Best for: buffering, async processing, “do later” workflows
  • Consumers poll and delete after success
  • Useful when processing can be delayed

📣 SNS — Pub/Sub notifications (push model)

  • Best for: broadcasting a message to many subscribers
  • Delivers immediately to all subscribers
  • Subscribers can be SQS, Lambda, Email, SMS, HTTP, etc.

🚌 EventBridge — Event routing (rules → targets)

  • Best for: event-driven architectures across AWS + custom apps
  • Rule-based matching + triggers targets
  • Supports schedules as well (hourly jobs, etc.)

Quick decision: Need buffering? → SQS. Need fan-out push? → SNS. Need rule-based event routing across services? → EventBridge.

✅ Exam Tips + Memory Hooks

  • 🧺 SQS = Queue: message stays until a consumer deletes it.
  • 📢 SNS = Topic broadcast: publish once → many subscribers receive.
  • 🚌 EventBridge = Rules + Targets: match events, trigger actions (also supports schedules).
  • 🧠 Popular pattern: SNS → SQS for fan-out + buffering.

One-liner recall: “Queue it (SQS), Notify it (SNS), Route it (EventBridge).” 🙂

Tip: In real projects, you usually send/receive via SDK (code). The console is mainly for setup and quick testing.
