Module 14 Reviewer: App Integration (SQS, SNS, EventBridge) 🔗📩

🧠 Topic: Workload-to-workload communication 🎯 Exam focus: Concepts & use-cases 🧩 Services: SQS • SNS • EventBridge
Big idea (in one line): When you run multiple apps in the cloud, you usually must connect them so they can share data/events—without making the whole system fragile. ✅

1) What problem are we solving? 🤝

In AWS, you can run workloads in different ways (EC2 🖥️, Lambda ⚡, Containers 🧱). Once you have more than one workload, the next challenge is integration:

  • How does App A notify App B that something happened?
  • How can services exchange data without breaking each other?
  • How do we handle spikes, retries, and failures?
Beginner-friendly example: An online shop 🛒
  • Order Service saves an order
  • Email Service sends confirmation
  • Inventory Service decreases stock

If Order directly calls Email and Inventory every time, a failure in one service can break the whole checkout flow. 😬

2) “Could” vs “Should”: Common integration approaches ✅⚠️

Direct calls (HTTP) 🌐

  • Works for: Simple systems, fast synchronous responses (e.g., “get product list”).
  • Risk: Tight coupling — if App B is down, App A may fail too.

Shared database ⚠️

  • Tempting because it’s “easy,” but often becomes a maintenance and security headache.
  • Apps become coupled through table structure and schema changes.

Event / message-based integration ✅

  • App A sends a message or event; App B processes it independently.
  • Supports buffering during traffic spikes, retries, and decoupling.
Key term: Decoupling 🔓 — Services can change, scale, or temporarily fail without taking down the entire system.

3) What you will learn in this section 📚

AWS provides dedicated services for cross-application communication. This module focuses on:

SQS 📥 — Message queue (buffer work)
  • Good for: asynchronous processing, smoothing traffic spikes
  • Common pattern: Producer → Queue → Consumer
SNS 📣 — Publish/Subscribe notifications
  • Good for: one message to many subscribers
  • Common pattern: Publisher → Topic → Subscribers
EventBridge 🧭 — Event bus & routing rules
  • Good for: event-driven architectures across many services
  • Common pattern: Event source → Bus → Rules → Targets

4) Quick mental model (easy comparison) 🧠✨

  • SQS = “Put tasks in a line; workers pick them up one by one.” 🧑‍🏭
  • SNS = “Broadcast an announcement to everyone subscribed.” 📢
  • EventBridge = “Send events to a bus; rules decide where they go.” 🚌
Mini scenario:
  • Order created → EventBridge routes event to multiple targets (billing, shipping, analytics)
  • Image uploaded → SQS queues resize jobs; Lambda/containers consume
  • System alert → SNS notifies email/SMS/HTTP endpoints

5) Terms you should remember for the exam 📝

  • Integration: Connecting workloads so they can communicate and share data.
  • Decoupling: Reducing direct dependencies to improve resilience and maintainability.
  • Synchronous (direct call): Caller waits for response. ⏳
  • Asynchronous (messages/events): Caller sends and continues; processing happens later. 🚀
  • Regional services: Many integration services are region-scoped (region choice matters). 🌍
