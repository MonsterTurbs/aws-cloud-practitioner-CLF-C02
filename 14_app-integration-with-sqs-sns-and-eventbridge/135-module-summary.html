App Integration — Module Summary (SQS, SNS, EventBridge, Step Functions)

AWS Certified Cloud Practitioner (CLF-C02) — Print-friendly reviewer / study guide

🧠 Focus: “connect apps and services” 🧩 Key services: SQS • SNS • EventBridge 🧭 Orchestration: Step Functions

1) Why App Integration matters 🌐

In the cloud, it’s common to have multiple applications running on different AWS services (EC2, Lambda, containers, etc.). They often need to exchange data or trigger each other — even if they are not on the same server and not in the same network.

✅ Goal: decouple systems so each app can evolve independently while still communicating reliably.

Why not just build a custom HTTP API? 🤔

  • Extra overhead: build, deploy, secure, and maintain an API.
  • More cost: you run/scale that API even if you only need “messaging.”
  • Harder to scale to many consumers: every consumer must integrate to your custom API.
  • Connectivity constraints: apps may need extra network work (VPC, security groups, routing).

2) The “Big 3” App Integration Services 🔁

Think of these as different communication styles:
  • SQS = “Put message in a queue; process later.” ⏳
  • SNS = “Broadcast push message to subscribers now.” 📣
  • EventBridge = “When an event happens, automatically trigger targets.” ⚡

SQS — Simple Queue Service 📥 (Asynchronous)

  • Producer app sends messages to a queue.
  • Consumer app polls the queue, processes messages, then deletes them (acknowledges success).
  • Great for decoupling and buffering spikes (traffic bursts).
🧩 Beginner mental model: Like a “to-do list” where workers pick tasks when ready.
Example (SQS) 🧪

Scenario: App A crawls websites. App B cleans data.

App A (producer)  →  SQS Queue  →  App B (consumer)

Message body example (JSON):
{
  "site": "example.com",
  "rawDataS3Key": "raw/example.com/2025-12-22.json"
}

App B reads message, cleans data, stores results, then deletes message.

SNS — Simple Notification Service 📣 (Push / Fan-out)

  • Publisher sends a message to an SNS Topic.
  • SNS pushes the message to all subscribers immediately.
  • Subscribers can be other AWS services (e.g., Lambda, SQS), HTTP endpoints, email, SMS, etc.
🧠 Beginner mental model: Like a group chat announcement — everyone subscribed gets the message.
Example (SNS Fan-out) 🧪 
App A → SNS Topic → (Subscriber 1) Lambda
                 → (Subscriber 2) SQS Queue
                 → (Subscriber 3) Email/SMS

Use-case: “New order created” triggers billing, shipping, and notifications.

EventBridge ⚡ (Event bus + rules)

  • Services (AWS or your apps) emit events.
  • You create rules that match events and route them to targets (Lambda, SQS, SNS, Step Functions, etc.).
  • Useful for event-driven architectures where producers don’t need to know who consumes the event.
🧠 Beginner mental model: Like an “IF this event happens… THEN trigger that action.”
Example (EventBridge) 🧪 
Event: "CrawlerFinished" emitted by App A
Rule: if detail-type == "CrawlerFinished" → trigger Lambda (App B)

Key idea: App A emits events; it doesn’t have to call App B directly.

3) Quick “Which one should I use?” decision guide 🧭

  • Use SQS when you want buffering, retry patterns, and consumers processing messages when ready (async). ⏳
  • Use SNS when you want a push broadcast to multiple subscribers right away (fan-out). 📣
  • Use EventBridge when you want event routing based on rules and a clean event-driven design (producers don’t know consumers). ⚡
Exam-friendly tip 🎯: If the question says “decouple and process later” → think SQS. If it says “notify many” → think SNS. If it says “react to events across services” → think EventBridge.

4) Step Functions 🪜 (Orchestrate workflows)

Step Functions helps you build reliable workflows by chaining steps (often Lambda functions) into a clear, repeatable execution sequence — including conditions and parallel branches.

  • Define steps (input → work → output).
  • Control flow: sequence, parallel, conditional branching.
  • Good for multi-step processes that must run in a well-defined order.
Example workflow 🧪 
OrderWorkflow:
1) ValidateOrder (Lambda)
2) ChargePayment (Lambda)
3) In Parallel:
   - UpdateInventory (Lambda)
   - NotifyCustomer (SNS/Lambda)
4) ShipOrder (Container/Lambda)
✅ Key takeaway: Step Functions is about orchestration (workflow logic), not just “send messages.”

5) Common exam confusions (fast clarifications) 🧩

  • SES vs SNS: SES sends emails to users; SNS sends notifications/messages to subscribers (services/endpoints). ✉️ vs 📣
  • SQS vs SNS: SQS = queue for later processing; SNS = immediate push to many. 📥 vs 📣
  • SNS + SQS combo: You can subscribe an SQS queue to SNS for fan-out + async buffering. 📣➡️📥
  • EventBridge vs SNS: EventBridge routes events using rules; SNS broadcasts messages to subscribers. ⚡ vs 📣

6) One-paragraph module recap ✅

This section focused on application integration — enabling different applications/services in AWS to communicate and share data without building expensive, fragile custom APIs. The main cloud-native tools are SQS (asynchronous queues), SNS (push notifications/fan-out), and EventBridge (event bus + rules that trigger targets). For multi-step processes that must run in a defined, reproducible order, Step Functions helps orchestrate complex workflows by chaining steps and passing outputs to the next step.
