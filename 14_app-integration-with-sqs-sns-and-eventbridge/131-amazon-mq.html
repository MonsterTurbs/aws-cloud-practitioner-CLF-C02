Amazon MQ — Reviewer / Study Guide

Topic: App Integration (Messaging) • CLF-C02 essentials • Single-column, A4 print-ready

🧠 Key idea: Managed open-source brokers ✅ Exam focus: When to choose MQ vs SQS/SNS 🧩 Brokers: ActiveMQ & RabbitMQ

1) What Amazon MQ is (in simple terms) 📬

Amazon MQ is AWS’s managed service for running open-source message brokers (specifically Apache ActiveMQ and RabbitMQ).

Think of a message broker as a “post office” between applications: one app sends a message, and another app receives it—without both apps needing to talk directly.

You use it when…
You want a broker you already know (ActiveMQ/RabbitMQ) but managed by AWS.
What AWS manages
Broker infrastructure (setup, maintenance, availability options), so you don’t run it on your own EC2.
Key contrast
Amazon MQ = open-source broker. SQS/SNS/EventBridge = AWS cloud-native messaging.

2) Why Amazon MQ exists (the “reason” question) 🎯

AWS already has its own messaging services like SQS (queues) and SNS (pub/sub). So why Amazon MQ?

  • ✅ Compatibility / migration: Many companies already use ActiveMQ or RabbitMQ on-premises.
  • ✅ Vendor constraints: Some systems require specific broker protocols or features.
  • ✅ Preference: Teams may want the familiar broker ecosystem/tools and keep the same mental model.
Exam-friendly phrasing: Amazon MQ primarily helps customers that don’t want to (or can’t) use AWS’s cloud-native solution such as SQS.

3) Quick comparison: Amazon MQ vs SQS/SNS (high-level) ⚖️

Amazon MQ (ActiveMQ/RabbitMQ) 🐇

  • Managed message broker service using open-source engines
  • Good for lift-and-shift or protocol compatibility needs
  • You’re adopting a broker model (with broker concepts)

SQS (Queue) 📥

  • AWS-native queue for asynchronous processing
  • Producers send messages, consumers poll and delete when processed
  • Great for decoupling, smoothing spikes, and worker pipelines

SNS (Pub/Sub) 📣

  • AWS-native push notifications to subscribers
  • One message can fan out to multiple targets (email, Lambda, SQS, HTTP endpoints, etc.)
  • Useful when receivers should react quickly

Rule of thumb (for CLF-C02):

  • Use SQS/SNS/EventBridge when you want AWS-native managed messaging with minimal broker management.
  • Use Amazon MQ when you specifically need ActiveMQ/RabbitMQ compatibility or are migrating existing broker-based systems.

4) Beginner example (simple scenario) 🧪

Imagine you have an order system:

  • 🛒 Order Service creates an order
  • 📦 Shipping Service prepares shipment
  • 📧 Email Service sends confirmation

Instead of calling each other directly, Order Service can publish a message like: 

{
  "event": "OrderCreated",
  "orderId": "ORD-12345",
  "customerId": "C-42"
}

With Amazon MQ, these services can use a familiar broker (ActiveMQ/RabbitMQ) to route messages. With SNS, Order Service could publish once and fan out to multiple subscribers. With SQS, each worker could pull messages when ready.

5) What to remember for the exam ✅

  • ✅ Amazon MQ = Managed Apache ActiveMQ and RabbitMQ on AWS.
  • ✅ It exists mainly for compatibility (customers that can’t/don’t want SQS).
  • ✅ SQS is AWS’s own queue (cloud-native). Amazon MQ is an open-source broker alternative.

Note: For CLF-C02, the key is understanding the positioning and why you’d pick it—not the deep operational details.

6) Mini self-check (1 minute) 📝

  • Q: If a company already uses RabbitMQ and wants minimal code changes when moving to AWS, which service fits? ➜ Amazon MQ
  • Q: If you want AWS-native queueing for asynchronous workers, which service fits? ➜ SQS
  • Q: If you want to push one message to multiple subscribers quickly, which service fits? ➜ SNS
