🔐 AWS Reviewer: Network Access Control Lists (NACLs)

CLF-C02 study notes — print-friendly, single-column. Topic: how NACLs differ from Security Groups and how they relate to Public/Private Subnets.

🧠 Beginner-friendly 🧾 A4 print-ready 📌 VPC • Subnets • Traffic control ✅ Exam keywords: NACL, subnet-level, inbound/outbound

1) What is a NACL?

A Network Access Control List (NACL) is a set of network rules that controls traffic at the subnet level. Think of it as a “gatekeeper” placed at the entrance/exit of a subnet.

Key idea ✅
Security Group = controls traffic for a single instance (or ENI).
NACL = controls traffic for an entire subnet (affects all instances inside it).

Where it is attached

  • 📍 NACL is associated with a subnet.
  • 🖥️ Security Group is attached to instances (technically, their network interface).

2) Inbound vs Outbound rules

Just like Security Groups, NACLs have Inbound and Outbound rules. But the defaults are different.

🧱 Default NACL behavior (common default)

  • Inbound: allow all traffic (by default)
  • Outbound: allow all traffic (by default)

This matches the lecture: default NACL is permissive in both directions.

🛡️ Security Group default behavior (typical)

  • Outbound: allow all traffic (by default)
  • Inbound: restricted (often none or minimal until you add rules)

This matches the lecture: SG defaults are more restrictive for inbound traffic.

3) NACLs vs Security Groups vs Subnet type

You now have multiple “traffic control” concepts in AWS networking. Here’s the clean mental model.

🌐 Public vs Private Subnet (connectivity)

  • Public subnet: has a route to an Internet Gateway (IGW) → can have internet connectivity.
  • Private subnet: no direct IGW route → no direct internet connectivity.
Important ⚠️
Subnet type is about network connectivity. Even if you “allow HTTP” in a security group, an instance in a private subnet still won’t be reachable from the public internet.

🧩 NACL vs Security Group (control layer)

  • NACL: subnet-wide rule set (one-to-many effect)
  • Security Group: instance-level firewall
Common best practice ✅
In many real setups, Security Groups are the primary day-to-day control mechanism, while NACLs are used for broader subnet-level guardrails.

🧠 Extra exam-relevant details (easy to remember)

  • 🔁 Security Groups are stateful: if inbound is allowed, return traffic is automatically allowed.
  • ↔️ NACLs are stateless: you must allow traffic in both directions (inbound and outbound) as needed.
  • 🧾 NACL rules support ALLOW and DENY; Security Groups are allow-based (you block by not allowing).

These help you distinguish NACL questions in exams: “stateless”, “subnet-level”, “explicit deny”, “rule order”.

4) Simple examples

Example A: Web subnet + DB subnet

Imagine a classic setup:

  • 🖥️ Web EC2 in a public subnet (needs inbound HTTP/HTTPS from the internet)
  • 🗄️ DB EC2 in a private subnet (should NOT accept inbound from the internet)
How controls work 🧭
  • Public/Private subnet decides if internet connectivity exists.
  • NACL can apply a subnet-wide guardrail (e.g., block a risky port across the whole subnet).
  • Security Group fine-tunes which ports are allowed per instance (e.g., web allows 80/443; DB allows only DB port from web subnet).

Example B: Block a port for the entire subnet

Suppose you want to ensure that no one inside a subnet can ever receive inbound traffic on a specific port (e.g., a legacy admin port). A NACL is a good “broad brush” tool for this.

  • 🚫 Add an inbound DENY rule on that port at the subnet’s NACL.
  • ✅ Even if someone later misconfigures a Security Group, the NACL still blocks at the subnet boundary.
Reminder ⚠️
Because NACLs are stateless, you must also consider outbound rules and return paths, depending on the flow.

5) Quick Review (Exam-style)

  • ✅ NACLs are associated with subnets, not individual instances.
  • ✅ NACLs have inbound and outbound rules.
  • ✅ Default NACL often allows all inbound and all outbound traffic.
  • ✅ Security Groups are usually the recommended day-to-day control mechanism for instances.
  • ✅ Public/Private subnet is about internet connectivity (route to IGW), not just “ports allowed”.
  • ✅ Security Groups are stateful; NACLs are stateless.
  • ✅ NACLs can have explicit DENY rules (useful as subnet-wide guardrails).
Common confusion ❌
“I allowed HTTP in the Security Group, so my private subnet instance should be reachable.”
Not true — the subnet’s routing (public vs private) still controls internet reachability.

6) Mini-glossary

  • VPC 🏢 — your virtual network in AWS (regional).
  • Subnet 🧱 — a smaller network segment inside a VPC (lives in a single AZ).
  • NACL 🧾 — subnet-level traffic rules (inbound/outbound).
  • Security Group 🛡️ — instance-level firewall rules.
  • IGW 🌍 — Internet Gateway (connects VPC to the internet).

Tip: If an exam question says “subnet-level rules” or “stateless” or “explicit deny”, think NACL. If it says “instance firewall” or “stateful”, think Security Group.
