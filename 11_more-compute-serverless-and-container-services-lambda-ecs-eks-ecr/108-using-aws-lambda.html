⚡ AWS Lambda — Using the Service (Console Workflow)

Reviewer / Study Guide (Beginner-Friendly) • Single-column • A4 print-ready

📌 Topic: Creating & configuring Lambda functions 🌍 Note: Lambda is regional (region selection matters) 🧠 Focus: Console steps + triggers + key settings

1) Big Idea (What you’re doing when you “use Lambda”) 💡

In AWS Lambda, you create functions. A Lambda function is the container for your code + configuration. It runs when something triggers it (an event), such as an S3 file upload.

Key exam takeaway ✅: Lambda is event-driven and regional. The region you select affects where the function exists and which resources it can easily interact with.

2) Where you access Lambda 🧭

  • ✅ Management Console (easiest UI for learning)
  • 💻 AWS CLI (automation / scripting)
  • 🧩 SDK (code-based automation from apps)

Beginner tip 🙂: Start with the Console to understand the moving parts (function, trigger, role, settings). Later, use CLI/SDK for repeatable deployments.

3) Creating a Lambda function (Console) 🏗️

In the Lambda console, you create a function using either:

  • 🆕 Start from scratch — you choose name, runtime, role, etc.
  • 🧪 Blueprint — AWS-provided examples to learn faster

3.1 Minimum choices you must make

🏷️ Function name

Example: demo1. Use meaningful names in real projects (e.g., image-resize-on-upload).

🧑‍💻 Runtime (programming language)

Choose a supported runtime (e.g., Node.js). Non-listed languages are possible via custom runtimes, but not the easiest path for beginners.

🧠 Architecture

Select the processor type under the hood (you don’t select a specific “instance type”).

🪪 Execution role (IAM role)

Defines what your function is allowed to do (e.g., read/write to S3). Lambda can create a basic role for you (commonly includes permission to write logs).

Common pitfall ⚠️: Your function might fail even if your code is correct, because the role doesn’t allow the needed action (example: reading from an S3 bucket).

3.2 Optional (but important) setting: VPC access 🧩

You can attach the Lambda function to a VPC if it needs to talk to private resources (e.g., an RDS database in a private subnet). You’re not “placing servers” inside a subnet, but you’re granting the function network access to that VPC.

4) Adding code to the function 🧾

You can provide your Lambda code in multiple ways:

  • ✍️ Edit directly in the Console (quick demos / learning)
  • 📦 Upload a ZIP (common for simple deployments)
  • 🪣 Upload ZIP to S3 then reference it
  • 🐳 Provide a Docker container image (one packaging method; Lambda is still “run code”, not a full container orchestration platform)

Simple mental model 🙂: Lambda = “function + configuration”. How you deliver the code (console/zip/container) is just the packaging method.

5) Tuning execution settings (cost + performance) ⚙️

Even though you don’t manage servers, you still control a few knobs that influence performance and cost.

  • ⏱️ Timeout: max time your function is allowed to run before AWS stops it
  • 🧠 Memory: more memory can speed execution (often reduces runtime)
  • 🪪 Execution role: update if permissions change

Practical example ✅: Increasing memory might cost more per unit time, but if it makes the function finish much faster, total cost can stay similar (or even improve) because you pay for execution time.

6) Triggers (events) — the “when to run” part 🔔

A trigger is the event source that causes your Lambda function to execute. Lambda supports many AWS services (and some third-party sources) as triggers.

6.1 Example trigger: S3 Object Created 📤

You can connect S3 to Lambda so that when files are uploaded (created) in a bucket, your code runs.

  • 📌 Choose trigger: S3
  • 🪣 Choose bucket
  • 🧾 Choose event type: Object Created
  • 🔎 Add filters (optional): e.g., only .jpg / .jpeg files

Permissions reminder ⚠️: If your function needs to read the uploaded object or write a transformed file back, the execution role must allow those S3 actions.

6.2 Beginner-friendly scenario (end-to-end) 🧠

Imagine a photo upload workflow:

  • 👤 User uploads photo.jpg into an S3 bucket
  • 🔔 S3 emits an Object Created event
  • ⚡ Lambda runs: resizes/compresses the image
  • 🪣 Lambda writes the optimized image into another bucket (or another prefix)

Why this is powerful 🙂: You don’t run an always-on server just to wait for uploads. The code runs only when needed.

7) What you do NOT choose in Lambda 🚫

  • ❌ No EC2 instance type selection (you don’t pick t3.micro, etc.)
  • ❌ No OS install or patching (AWS manages that)
  • ❌ No manual provisioning of servers

You only choose a few high-level settings (runtime, architecture, timeout, memory, role, triggers), and AWS handles the rest.

8) Quick Checklist (Console) ✅

  • 🌍 Confirm the Region (Lambda is regional)
  • 🆕 Create function (scratch or blueprint)
  • 🏷️ Name + 🧑‍💻 runtime + 🧠 architecture
  • 🪪 Attach the correct execution role (permissions!)
  • 🧾 Add/Upload code (console / zip / S3 / container)
  • ⚙️ Set timeout + memory (balance cost vs performance)
  • 🔔 Add trigger (e.g., S3 Object Created)
  • 🔎 Add optional filters (e.g., only .jpeg)
  • 🧪 Test with a sample event and check logs (logging is typically part of the basic role)

9) Exam-oriented notes (CLF-C02) 🧩

  • 📌 Lambda runs code on events (event-driven compute).
  • 🌍 Lambda is regional (unlike CloudFront distributions which are global).
  • 🪪 IAM roles are critical: code can only access AWS resources it has permissions for.
  • 💰 You pay for execution time; idle does not cost the same way always-on servers do.

One-liner ✅: “Lambda = serverless, regional, event-driven function execution with IAM-controlled permissions.”

10) Micro-review (fast recall) 🧠

  • ⚡ Function = code + settings
  • 🔔 Trigger = event source (S3 upload, etc.)
  • 🪪 Role = permissions your code can assume
  • ⚙️ Timeout/Memory = performance & cost tuning knobs
