Single-column • A4 print-ready • Beginner-friendly notes, examples, and exam tips

1) Big Idea (in plain words)

🧱 Containers are “packages” that include your app + everything it needs to run (runtime, libraries, config). Instead of installing software on a server manually, you run containers built from images (often Docker images).

🧰 ECS and EKS help you launch, scale, and manage containers in AWS. You define what to run (images + settings), and AWS helps handle the operational work.

✅ Exam mindset: ECS/EKS = container orchestration. Fargate = serverless way to run containers.

2) Key Terms You Must Know

📦 Cluster
A logical group where your container workloads run. You create a cluster, then run tasks/services inside it.
🧾 Task Definition
The “blueprint” describing how to run containers: image, CPU/memory, ports, environment variables, IAM role, etc.
🏃 Task
A container run that usually finishes (batch job style). Example: run a nightly report, then stop.
🧑‍💼 Service
An ongoing task that should keep running (web server / API). ECS/EKS keeps the desired number running.
🛠️ Launch Type / Infrastructure
Where containers run: either EC2 (you choose instance types) or Fargate (serverless).
🚀 Fargate
Serverless container execution: you don’t manage EC2 instances. You specify CPU/memory; AWS runs it.

3) ECS vs EKS (What’s the Difference?)

🆚 Both run containers, but the “control plane” differs:

  • 🧩 ECS (Elastic Container Service): AWS-native container orchestration (simpler for many AWS-first teams).
  • ☸️ EKS (Elastic Kubernetes Service): managed Kubernetes (useful if you want Kubernetes portability/standard ecosystem).
📝 For CLF-C02: you typically just need to know ECS and EKS run containers, and EKS = Kubernetes.

4) How ECS/EKS Work (Workflow)

Think of it as: Define → Choose where to run → Deploy → Scale/Monitor ✅

  1. 🧾 Define task(s) (task definition): which image(s) to run + settings.
  2. 🏗️ Create a cluster: choose networking + infrastructure (EC2 or Fargate).
  3. 🏃 Run as a Task (one-off) or 🧑‍💼 Run as a Service (always-on).
  4. 📈 Scale and operate: set desired count, auto scaling, rolling updates, health checks.
  5. 🔍 Monitor: logs/metrics; investigate failures; adjust capacity/policies.
⚠️ Common confusion: “Task” vs “Task Definition”
  • Task Definition = blueprint (like a recipe)
  • Task = running instance of that blueprint (like the cooked dish)

5) Infrastructure Choices: EC2 vs Fargate

Option A — EC2 Launch Type 🖥️

  • You (or your team) choose EC2 instance types and how many instances to run in the cluster.
  • AWS helps orchestrate containers on those instances, but you still think in “servers.”
  • Good when you want more control, special instance types, or you already manage EC2 heavily.

Option B — Fargate (Serverless) ✨

  • You don’t manage EC2 instances.
  • You specify simplified settings like CPU and memory, and AWS runs the containers for you.
  • Popular choice because it reduces operational work (no “how many servers?” problem).
✅ CLF-C02 takeaway: Fargate = serverless containers used with ECS or EKS. You focus on the container/task; AWS focuses on the servers.

6) Mini Examples (Beginner-Friendly)

Example 1: One-off nightly job 🌙

You need a container to run a script daily (e.g., generate a report) and then stop.

  • Use an ECS/EKS Task (not a Service) ✅
  • Schedule it (e.g., once per day) 🗓️

Example 2: Web API that must always run 🌐

You need a containerized Node.js API that should always be available.

  • Use an ECS/EKS Service ✅
  • Set desired count (e.g., 2 tasks) for redundancy 📌
  • Optionally place a Load Balancer in front ⚖️

Example 3: “I don’t want to manage servers” 🙅‍♂️

You still want containers, but you don’t want to pick EC2 types or keep track of instances.

  • Choose Fargate ✅
  • Provide CPU/memory; AWS runs it ✨

7) Task Definition (What You Configure)

🧾 A task definition describes how to run your container(s). Typical settings include:

  • 📦 Image name (e.g., from a registry like Amazon ECR)
  • 🧠 CPU + memory limits
  • 🔌 Ports to expose (e.g., 80/443/3000)
  • 🌱 Environment variables (e.g., NODE_ENV=production)
  • 🔐 IAM role (permissions for the running task to access AWS services)
  • 🌐 Networking mode + security settings

Simple “pseudo” task definition idea (for understanding):

{
  "container": {
    "image": "my-app:1.0",
    "cpu": 256,
    "memory": 512,
    "portMappings": [3000],
    "env": {"NODE_ENV": "production"}
  }
}
📝 You do not need to memorize JSON fields for CLF-C02. Just know the concept: task definition = container blueprint.

8) Networking & Security (High-Level)

  • 🌐 You typically run clusters inside a VPC.
  • 🧱 You configure subnets and security groups so containers can reach what they need.
  • 🔐 You can grant containers permissions via IAM roles (e.g., write to S3).
✅ Exam-friendly mental model: Security Groups control network traffic, IAM Roles control AWS permissions.

9) Operations: Scaling, Monitoring, and Scheduling

Scaling 📈

  • Services can maintain a desired count (e.g., always keep 3 tasks running).
  • You can scale up/down based on demand (auto scaling concepts).

Monitoring 🔎

  • Check if containers are healthy, restarting if needed.
  • View logs/metrics to detect issues and tune performance.

Scheduling 🗓️

  • Run tasks once per day/week/month (batch-style jobs).
  • Keep services always running (web workloads).

10) When to Use What (Simple Decision Guide)

  • ⚙️ Want maximum control + you’re comfortable managing servers → EC2 launch type
  • ✨ Want containers but minimal server management → Fargate
  • 🧩 Want AWS-native orchestration and simpler onboarding → ECS
  • ☸️ Want Kubernetes ecosystem/skills/portability → EKS
⚠️ Don’t confuse Lambda vs Fargate:
  • ⚡ Lambda: event-driven functions (short-running code)
  • 📦 Fargate: run containers without managing servers
