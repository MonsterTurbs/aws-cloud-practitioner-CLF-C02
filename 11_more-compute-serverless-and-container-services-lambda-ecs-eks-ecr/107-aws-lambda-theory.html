🌟 Big Idea: What is AWS Lambda?

AWS Lambda is a serverless compute service that runs your code when something happens (an event). 🧩

  • ✅ You focus on the code and the trigger (event source).
  • ✅ You do not manage servers, operating systems, or manual scaling.
  • 💡 Think: “Run this function when X happens.”
Simple mental model:
Event ➜ triggers ➜ Lambda Function (your code) ➜ does work (e.g., resize image, write to DB, send email).
🧭 How Lambda Works (End-to-End)
  1. You provide code (function) 📦
  2. You pick a trigger (event source) 🔔
  3. AWS runs your code when the event occurs ⚙️
  4. You pay only while it runs (milliseconds of execution) ⏱️💸

🧪 Example scenario (S3 upload)

  • Event: user uploads an image to S3 🖼️
  • Lambda: resizes the image and saves a smaller copy 🪄
  • Result: your website loads thumbnails faster 🚀

🌐 Example scenario (HTTP request)

  • Event: an HTTP request hits an API endpoint 📬
  • Lambda: validates request, stores data, returns response ✅
  • Common use: lightweight APIs, webhooks, background tasks 🧰
📦 How You Provide Code to Lambda

You can get your code into Lambda in multiple ways:

  • 📝 Write/edit in the Lambda Console (good for demos and learning)
  • 📁 Upload a ZIP file (common for real projects)
  • 🐳 Provide a Docker container image (a packaging method)
Important clarification ⚠️

Even if you provide a Docker container image, Lambda is still mainly a code execution service (not a container platform like ECS/EKS). A container image here is just a convenient packaging format.

Programming languages: AWS supports multiple runtimes out of the box (e.g., Node.js, Python, Java, etc.). In theory, you can support more using custom runtimes, but for the exam, remember: Lambda supports several common languages out of the box. ✅

🔔 Event Sources (Triggers)

Lambda runs because an event source triggers it. You can have many kinds of triggers and even multiple triggers for the same function. 🔁

  • 🪣 S3 events (e.g., object uploaded / deleted)
  • 🌐 HTTP/API events (often via API services)
  • 📨 Messaging events (queues/streams, depending on architecture)
  • ⏰ Scheduled events (run on a timer)
Filtering 🎯

You can often filter events so Lambda only runs for some cases (e.g., only when files with .jpg are uploaded, or only within a certain prefix/path).

⚙️ Key Configuration Settings (What You Still Control)

You don’t manage the server, but you do configure the execution environment and behavior.

  • ⏳ Timeout: maximum runtime before AWS stops the function (controls cost + runaway code).
  • 🧠 Environment variables: dynamic values your code can read (e.g., BUCKET_NAME, STAGE).
  • 🧱 Architecture: choose the processor type (high-level choice; not exact hardware).
  • 🗂️ Attach file systems (EFS) if needed for shared file access.
  • 🔐 Permissions via an execution role (covered below).

🧩 Mini example: environment variables

Instead of hardcoding values, set an environment variable:

BUCKET_NAME = "my-app-uploads"
THUMBNAIL_WIDTH = "300"

Your function reads these values at runtime, so you can change behavior without changing code. ✅

💸 Pricing + Free Tier (High-Level)
  • ✅ You pay for the time your code runs (per millisecond).
  • ✅ If the function is idle (not running), you’re not paying for “a server waiting.”
  • 🆓 Lambda has a monthly free tier that renews every month (useful for learning/testing).
Exam-friendly wording 🧠

Lambda follows a pay-per-use model: cost is tied to executions and execution duration, not to a continuously running instance.

🪪 Execution Role (Permissions for Your Code)

Lambda code often needs to call other AWS services. Example: write a file to S3, publish a message, read from a database, etc.

To allow that, you attach an execution role (an IAM role) to the function. 🔐

  • ✅ The function assumes the role while running.
  • ✅ The role defines what the function is allowed to do.
  • ⚠️ Best practice idea: grant least privilege (only the permissions needed).

🧪 Example permission need

  • Lambda resizes an image
  • Then it must putObject into another S3 bucket
  • So the role must allow S3 write actions for that bucket ✅
🕸️ VPC Access (When Lambda Must Reach Private Resources)

Lambda does not “live inside” your VPC like an EC2 instance does, but you can connect a function to a VPC to reach private resources. 🧷

  • ✅ Useful when Lambda must talk to private EC2 instances or private databases.
  • ✅ You configure which VPC/subnets/security controls apply for that access path.
  • 💡 Key idea: this is about network access, not about you managing servers in a subnet.
Beginner reminder 🙂

If your database is in a private subnet, you typically don’t want the public internet talking to it directly. Lambda (or an app server) can talk to it over private networking when configured correctly.

📝 Quick Exam Tips / Common Confusions
  • ⚡ Lambda = event-driven serverless compute (runs code because something happened).
  • ⏱️ Pay per execution time, not per running server.
  • 🔔 Many triggers can invoke the same function (S3, HTTP, schedules, etc.).
  • 🪪 If Lambda needs access to other AWS services, it needs an execution role.
  • 🐳 Container image is just a packaging option; Lambda is not primarily a container orchestration service.
  • 🕸️ Lambda can be configured for VPC access if it must reach private resources.
One-liner to memorize 💡
“Lambda runs code on demand in response to events, with automatic scaling and pay-per-use billing.”
