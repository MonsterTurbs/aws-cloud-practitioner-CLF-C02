AWS CLF-C02 Reviewer: S3 vs EBS vs EFS

Single-page, A4 print-ready study guide (beginner-friendly) — focus: what each service is, when to use it, and exam cues.

Big Picture 🧭: All three store files, but they do it in different ways. There is no “best” service—pick based on how your app needs to access files (disk attached to one server, shared file system, or object storage).

1) Quick Definitions (Memorize These)

💽 EBS (Elastic Block Store) Block storage

Think: “Attachable hard drive” for EC2 only.

  • Acts like a raw disk you attach to an EC2 instance (you format/mount inside the OS).
  • Best when your EC2 workload needs extra disk space and low-latency disk access.

🗂️ EFS (Elastic File System) Managed file system

Think: “Shared network folder” you can mount from multiple compute services.

  • Provides a ready-to-use, scalable file system (you manage folders/files, not disks).
  • Designed for multi-access (many instances/services can read/write).

📦 S3 (Simple Storage Service) Object storage

Think: “Unlimited storage buckets for files” accessed via API/console/CLI.

  • Stores objects (files) in buckets—no traditional disk or mounted file system.
  • Can be used with or without EC2 (upload/download directly).

Memory trick: EBS = Disk, EFS = Shared Folder, S3 = Bucket of Objects.

2) When to Use What (Simple Scenarios)

  • ✅ Use EBS when you need a disk attached to one EC2 instance (e.g., database volume, app files on a single server).

    Example: You run a single EC2 web server and want extra space for logs or a local DB → attach an EBS volume.

  • ✅ Use EFS when multiple instances/services must share the same files (e.g., shared uploads folder, shared configs).

    Example: Auto Scaling group of EC2 instances needs a shared /uploads directory → mount EFS on all instances.

  • ✅ Use S3 when you want simple, scalable file storage accessed via API (uploads, backups, static website files, archives).

    Example: Users upload images → store in S3; your app reads them via URL/API. No server disk management needed.

3) Key Differences (Exam-Friendly)

🔌 “Attach to compute” vs “Standalone storage”

  • EBS and EFS are typically used by compute services (mounted/attached).
  • S3 is standalone—you can upload/download without running EC2 at all.

📈 Scaling

  • S3: effectively “unlimited” scaling for objects (you don’t provision capacity).
  • EFS: built for automatic scaling of a managed file system.
  • EBS: volume-based; can scale, but is closer to “disk management” and may require more planning/ops work.

👥 Multi-access

  • EFS: designed for many instances/services reading/writing the same file system.
  • EBS: can support multi-attach in specific cases, but it’s not the typical default pattern and can be tricky.
  • S3: many clients can access objects; it’s not a mounted shared file system.

🧠 “What do I manage?”

  • EBS: you manage formatting/mounting (like a raw disk).
  • EFS: you manage folders/files, AWS manages the underlying storage.
  • S3: you manage objects (files) + permissions (buckets/policies), not disks or file systems.

4) Common Mistakes (Avoid These) ⚠️

  • Mixing up EFS vs S3: EFS is a mounted file system; S3 is object storage accessed via API/console/CLI.
  • Trying to use EBS without EC2: EBS is effectively EC2-focused for attachment.
  • Assuming “public by default” in S3: by default, buckets/objects are typically locked down; public access requires explicit configuration.

5) Exam Cues (What Keywords Usually Mean) 📝

  • “Attach a volume / disk to EC2” → EBS
  • “Shared file system mounted by multiple EC2 instances” → EFS
  • “Store files in buckets / object storage / archive / static website hosting” → S3

Tip: If the question talks about buckets or storage classes, it’s almost certainly S3.

One-line recap ✅: EBS = disk for EC2, EFS = shared managed file system, S3 = scalable object storage you can use from anywhere.
