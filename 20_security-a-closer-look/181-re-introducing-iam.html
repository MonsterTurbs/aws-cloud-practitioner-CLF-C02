🌟 What IAM is (in plain words)

IAM (Identity and Access Management) is the AWS service you use to control who can access your AWS account and what they are allowed to do. Think of it like a security guard + rulebook for AWS.

Simple analogy: 🏢

  • Identities = people and “work badges” (users, groups, roles)
  • Policies = written rules about what badge holders can do
  • Services = rooms in the building (S3, EC2, RDS, etc.)
Exam mindset: IAM is one of the most important “account protection” topics. You should be comfortable with identities + permission logic.

👥 IAM identities: Users, Groups, Roles

🙋‍♂️ Users
Human identities (employees) that log in and work in AWS.
  • Usually have a username/password for console access and/or access keys for CLI/SDK.
  • Best practice: avoid using the root user for daily tasks.
👨‍👩‍👧‍👦 Groups
A way to manage permissions for multiple users at once.
  • Add users to a group → they inherit the group’s policies.
  • Example: “Developers” group gets read-only access to CloudWatch + limited S3 access.
🎭 Roles
Identities typically assumed by AWS services or trusted users for temporary access.
  • Common for services: e.g., EC2 role that allows EC2 to read S3 objects.
  • Also used for cross-account access (advanced, but good to recognize).

🧪 Mini example

You have an app running on EC2 that needs to upload logs to S3. Instead of storing S3 credentials inside your app code (bad idea 😬), you attach an IAM role to the EC2 instance with a policy that allows s3:PutObject to a specific bucket.

📜 Policies: the permission rulebook

IAM permissions are typically defined using policies (JSON documents) that contain permission statements.

✅ Key rule to memorize

  • By default, a new identity has no permissions (implicit deny).
  • You must explicitly allow actions using policies.
  • An explicit deny always overrides an allow.

🧩 AWS managed vs Customer managed policies

  • AWS managed policies (pre-built): quick for common use cases (e.g., ReadOnlyAccess).
  • Customer managed policies (your own): best for real-world least-privilege setups.
  • You can attach multiple policies to a user/role/group (permissions combine).

🔎 Very small JSON example (concept only)

You don’t need to write JSON for CLF-C02, but recognize that policies are JSON-based.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::example-bucket"]
    }
  ]
}

🧠 How IAM decides: Allow vs Deny (quick mental model)

  1. Start with implicit deny (no access by default).
  2. If any statement allows the action → access may be granted…
  3. …but if any statement has explicit deny → access is denied (deny wins).

For the exam, remember: explicit deny overrides explicit allow.

🛠️ IAM features to know (highlighted in the lecture)

1) 🧱 Creating policies: Visual editor vs JSON editor

  • Visual editor: pick a service → choose actions → set resources/conditions (great for beginners 🙂).
  • JSON editor: directly write policy JSON (common for advanced users).

2) 🧭 Access Advisor (per identity)

Access Advisor helps you see which services an identity (user/role) has access to and when those permissions were last used.

Why it matters: you can discover permissions that were granted but never used → remove them to follow least privilege ✅

3) 🕵️ Access Analyzer (zone of trust)

Access Analyzer helps identify policies that might allow access to resources from outside your account / outside your trusted boundary (your “zone of trust”).

  • Useful for finding overly broad access that could cause accidental exposure.
  • Think: “Did we accidentally allow external access?” 😬
Practical takeaway: Use Access Advisor to remove unused permissions, and Access Analyzer to catch unintended external access.

✅ Quick Check (exam-style recall)

  • Q: What are the three IAM identity types?
    A: Users, Groups, Roles.
  • Q: What’s the default permission state of a new IAM user?
    A: No permissions (implicit deny).
  • Q: What overrides an Allow?
    A: Explicit Deny.
  • Q: Which tool helps find permissions that were granted but not used?
    A: Access Advisor.
  • Q: Which tool helps detect access from outside your trusted boundary?
    A: Access Analyzer.

🧷 CLF-C02 exam tips (high value)

  • Always associate IAM with account protection and least privilege 🔒
  • Remember the difference: Users = humans, Roles = assumed access (often services).
  • Policies are JSON documents with statements; you don’t need to write them, but recognize them.
