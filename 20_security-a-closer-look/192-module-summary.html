Security — Module Summary (AWS CLF-C02)

Print-friendly reviewer / study guide (single-column, A4-ready) • Focus: what each security service does and when to use it.

🔐 Account protection 🧾 Compliance 🛡️ Workload + network protection 🔒 Data protection 📌 Exam-ready associations

1) Big picture: what “secure cloud” really means

✅ Core idea

A secure AWS environment is a combination of controls: you protect the account (who can log in + what they can do), stay compliant, protect workloads and traffic, and protect data (including secrets). No single service does everything.

🧠 Think in 4 layers

  • Account: identities, permissions, suspicious actions
  • Compliance: enforce rules, produce audit evidence
  • Workloads + Network: vulnerabilities, investigation, firewalls, DDoS
  • Data: encryption, secrets, sensitive-data discovery

2) Quick Map: “Which AWS service solves which security problem?”

  • 🔐 Identities & permissions → IAM
  • 🧑‍💼 Single sign-on (corporate login) → AWS Single Sign-On / IAM Identity Center + Directory Service
  • 🧾 Track “who did what” (API audit log) → CloudTrail
  • 🚨 Detect suspicious activity automatically → GuardDuty
  • 🧪 Scan EC2 / containers for vulnerabilities → Inspector
  • 🕵️ Investigate incidents (what happened?) → Detective
  • 🧱 Block malicious web requests (SQLi/XSS) → WAF
  • 🔥 Inspect/block traffic at network level → Network Firewall
  • 🧩 Manage firewall rules at scale → Firewall Manager
  • 🌊 DDoS protection → Shield (Standard / Advanced)
  • 🔐 Encryption keys (managed) → KMS
  • 🏦 Own key control (hardware) → CloudHSM
  • 🔏 Encrypt data in transit (TLS certificates) → ACM
  • 🗝️ Store secrets (DB credentials, API keys) → Secrets Manager
  • 🧬 Find sensitive data in S3 + exposure → Macie
  • 📜 Enforce configuration rules → AWS Config
  • 🧾 AWS compliance reports → Artifact
  • 🧑‍⚖️ Audit evidence + reports → Audit Manager
  • 🏢 Multi-account management → Organizations + Resource Access Manager (RAM)
  • 📊 One place to view security posture → Security Hub

3) Account security & access control

🔐 IAM (Identity and Access Management)

What it is: The core service for who can access AWS and what they can do.

  • Identities: Users (people), Groups (permissions bundles), Roles (usually for AWS services/apps)
  • Policies: Permission statements attached to identities
  • Default is deny; you must explicitly allow actions
  • Explicit Deny overrides Allow
🧩 Beginner example

You have a developer who should only read from S3. You attach a policy that allows s3:GetObject and s3:ListBucket, but not delete. Result: they can view files but can’t remove them.

  • Access Advisor: shows when granted permissions were last used (helpful for removing unused access)
  • Access Analyzer: flags resources that may be accessible from outside your account (“outside your zone of trust”)

🧑‍💼 Single Sign-On and Directory Service

Goal: Make login easier and more standardized in larger environments.

  • Single sign-on means employees use one set of credentials across systems (e.g., corporate account).
  • For multi-account environments (Organizations), use AWS SSO / IAM Identity Center so one identity can access multiple accounts.
  • Directory Service helps integrate Microsoft Active Directory with AWS.
🧩 Beginner example

Your company already uses Microsoft AD for employee accounts. Directory Service helps connect those existing logins to AWS, so employees don’t need separate AWS-only usernames/passwords.

🧾 CloudTrail (audit trail)

What it is: Records AWS API activity so you can answer: Who did what, when, from where?

  • Great for investigating suspicious behavior after the fact
  • Useful when credentials are compromised or when insider risk exists

🚨 GuardDuty (threat detection)

What it is: Automated detection of suspicious activity using ML/patterns.

  • Helps you spot problems without manually reading CloudTrail logs
  • Best fit: large environments where “too many things happen” to audit manually
🧠 Memory hook

CloudTrail = recording 📼. GuardDuty = alarm system 🚨.

4) Multi-account security building blocks

🏢 Organizations (multi-account management)

Why it matters for security: Many security services can work across accounts, and you want central governance.

  • Group accounts, manage centrally, and apply organization-wide controls
  • Works with services that support organization-wide visibility and controls

🔁 Resource Access Manager (RAM)

What it does: Securely share actual resources across accounts (not templates/blueprints).

🧩 Beginner example

Account A (network team) owns a VPC. Account B (app team) needs to deploy into that VPC. RAM lets Account B use the shared VPC without getting full admin control over it.

5) Compliance

📜 AWS Config

What it does: Define configuration rules and detect non-compliant resources.

  • Think “policy enforcement for configurations” (guardrails for how resources should be set up)
  • Helps you detect drift: someone changes a setting that violates your rule

🧾 Artifact

What it does: Download AWS compliance reports and agreements (AWS-level compliance evidence).

Useful when auditors ask: “Is AWS compliant with standard X?” Artifact provides AWS documentation to support that.

🧑‍⚖️ Audit Manager

What it does: Helps generate audit-ready reports for your own controls, collecting evidence from AWS services.

  • Define audit frameworks/requirements
  • Collect and package evidence to show compliance

6) Workload protection and incident investigation

🧪 Amazon Inspector

What it does: Automated vulnerability scanning for EC2 instances and containers.

  • Finds known vulnerabilities (e.g., vulnerable packages/software)
  • Gives details on what’s affected so you can patch or remediate
🧠 Memory hook

Inspector = “What’s vulnerable?” 🔍

🕵️ Amazon Detective

What it does: Helps investigate incidents and suspicious activity (who/what/when relationships).

  • Explore resources (users, roles, instances) and their related events
  • Supports “root cause” investigation: what happened and how it spread
🧠 Memory hook

Detective = “What happened?” 🕵️

7) Network protection: firewalls and traffic filtering

🧱 Security Groups and NACLs (baseline controls)

  • Security Groups: instance-level firewall (stateful)
  • NACLs: subnet-level network rules (stateless)

These control traffic mostly by ports/protocols/IPs. They are essential, but not enough for “content-based” web attacks.

🧩 WAF (Web Application Firewall)

What it does: Inspect HTTP(S) requests and block based on request metadata/body.

  • Can help block common web attacks like SQL injection and XSS
  • Useful when traffic targets a valid port but the request content is malicious

🔥 Network Firewall

What it does: Managed firewall for network-level inspection and rules across networks/subnets/VPCs.

  • Inspect protocol, IPs, ports, and more detailed traffic properties
  • Supports stateless and stateful rule configurations

🧰 Firewall Manager

What it does: Central management of firewall rules (WAF, Network Firewall, etc.) across accounts/environments.

Think “one place to manage firewall policies” when you have many accounts or many applications.

8) DDoS protection

🌊 AWS Shield

  • Shield Standard: free and enabled by default (basic protection)
  • Shield Advanced: paid, more features (anomaly detection, customization, specialized support)
🧩 Beginner explanation

DDoS is “too many normal-looking requests at once.” Firewalls may not block it because each request looks valid. Shield focuses on identifying and stopping those attack patterns at scale.

9) Data protection: encryption, secrets, and sensitive-data discovery

🔐 Encryption at rest: KMS vs CloudHSM

  • KMS (Key Management Service): managed keys, easy integration with services like S3
  • CloudHSM: hardware security module; more control (bring/manage your own key store)
✅ Exam-level takeaway

Turn on encryption for major services. KMS is the default “managed” approach; CloudHSM is for stronger self-managed key control.

🔏 Encryption in transit: ACM

ACM (AWS Certificate Manager) helps you use SSL/TLS certificates to encrypt traffic to/from services like CloudFront and ALB.

🗝️ Secrets Manager

Problem: You must not hardcode secrets (DB username/password, API keys) in code.

Solution: Store secrets securely in Secrets Manager and retrieve them at runtime (e.g., via AWS SDK).

🧩 Beginner example

Instead of writing dbPassword = "mypassword" in code, your app requests it from Secrets Manager when it starts. Only the app role is allowed to read that secret.

🧬 Amazon Macie

What it does: Scans S3 objects to identify sensitive data and flags risky exposure (public buckets, unencrypted sensitive files).

  • Uses machine learning + optional custom rules
  • Helps prevent accidental data exposure

10) Consolidated dashboards

📊 Security Hub

What it does: Consolidated security posture view, grouping key findings across services.

  • Integrates key services like GuardDuty, Inspector, and Macie
  • Helps manage findings and actions centrally, including across accounts

11) Exam practice: quick Q&A (flashcard style)

  1. Q: Which service helps you see “who created an S3 bucket” or “who started an EC2 instance”?
    A: CloudTrail 🧾 — it records API actions so you can audit activity.
  2. Q: You want automated alerts for suspicious activity, not manual log reading. What do you enable?
    A: GuardDuty 🚨.
  3. Q: You need to block web attacks like SQL injection and XSS based on request content.
    A: WAF 🧱.
  4. Q: You want to scan EC2 instances/containers for known vulnerabilities.
    A: Inspector 🧪.
  5. Q: You suspect an incident happened and need investigation tooling to understand it.
    A: Detective 🕵️.
  6. Q: You need to store DB credentials securely and avoid hardcoding them in code.
    A: Secrets Manager 🗝️.
  7. Q: You want to find sensitive data in S3 and detect if it’s exposed publicly.
    A: Macie 🧬.
  8. Q: You want encryption keys managed for you and tightly integrated with AWS services.
    A: KMS 🔐.
  9. Q: DDoS protection that is enabled by default for AWS accounts?
    A: Shield Standard 🌊.
  10. Q: Where do you download AWS compliance reports for audits?
    A: AWS Artifact 🧾.

12) Final checklist for this module

  • ✅ I can map each service to a security problem (IAM vs CloudTrail vs GuardDuty vs Security Hub).
  • ✅ I understand the difference between prevention (WAF, Network Firewall, Inspector) and detection/investigation (GuardDuty, Detective, CloudTrail).
  • ✅ I know encryption: at rest (KMS/CloudHSM) and in transit (ACM).
  • ✅ I can explain how to avoid exposing credentials (Secrets Manager) and how to detect sensitive S3 exposure (Macie).
  • ✅ I know compliance tools: Config, Artifact, Audit Manager.
