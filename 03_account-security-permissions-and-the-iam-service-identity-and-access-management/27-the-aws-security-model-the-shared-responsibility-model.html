27 — The AWS Security Model: Shared Responsibility Model 🔐🤝

Reviewer / Study Guide (single-column, A4 print-ready)

🎯 Lecture Goal

Understand the AWS Shared Responsibility Model and memorize its key principle: security in AWS is shared between AWS and the customer (you).

Key principle ✅ If AWS controls it, AWS secures it. If you control/configure it, you must secure it.

🤝 What Is the Shared Responsibility Model?

The Shared Responsibility Model explains who is responsible for what when it comes to security in AWS.

🛡️ AWS responsibility

AWS is responsible for securing what it controls—mainly the underlying infrastructure and AWS internal operations.

🔧 Your responsibility (customer)

You are responsible for securing what you control—your account access, your configurations, and your workloads (apps/code).

Simple memory hook ✅ AWS = security “OF” the cloud • You = security “IN” the cloud.

🛡️ AWS Responsibilities (What AWS Secures)

From the lecture: AWS secures the things you can’t control, especially the physical infrastructure.

  • 🏢 Data centers (physical security)
  • 🖥️ Physical servers / hardware “under the hood”
  • 🧵 Internal systems & processes (including preventing malicious internal behavior)
  • ⚙️ Managed services security: if you can’t configure something, it’s not your job to secure it

Key idea ✅ If a service is highly managed (fewer configuration options), AWS takes on more security responsibility for that service.

🔧 Your Responsibilities (What You Must Secure)

From the lecture: you must secure everything you can configure and control.

  • 🧑‍💻 Your applications/workloads (your app behavior and runtime security)
  • 🧾 Your application code (avoid vulnerabilities, safe coding practices)
  • ⚙️ Software you install/configure on rented servers
  • 🔑 Your AWS account access (who can log in and do what)
  • 🧩 Configuration choices you make (permissions, network rules, settings)

Common risk ⚠️ Even if AWS secures the infrastructure, a misconfigured account/service on your side can still lead to breaches or unexpected costs.

🧪 Beginner-Friendly Example (Server vs Managed Service)

Example A: Renting a server (self-service) 🖥️

If you rent a server and install software yourself:

  • AWS secures the physical hardware and data center
  • You secure the operating system and installed software (updates, configuration, vulnerabilities)

Example B: Using a managed service 🧰

If you use a managed service with limited configuration:

  • AWS secures more layers (because you can’t manage them)
  • You still secure access and your usage (who can connect, what data you store, etc.)

Rule of thumb ✅ The more “managed” the service, the less infrastructure/security maintenance you do—but you still own access control and correct configuration.

🧠 Exam Tip: How to Answer Shared Responsibility Questions

When a question asks “who is responsible?” use this decision flow:

  1. 1) 🧩 Can the customer configure/control it?
  2. 2) ✅ If yes → it’s the customer’s responsibility (secure it).
  3. 3) 🏢 If no (it’s underlying infrastructure / AWS internal operations) → it’s AWS’s responsibility.

Fast clue ✅ Words like “data center,” “physical hardware,” “AWS internal systems” → AWS. Words like “your app,” “your code,” “your configuration,” “account access” → You.

✅ Quick Self-Check

Q1: What is the key principle of the Shared Responsibility Model?

A: Security responsibilities are shared—AWS secures what it controls; customers secure what they control/configure.

Q2: Who secures AWS data centers and physical infrastructure?

A: AWS.

Q3: Who is responsible for securing your application code and workloads?

A: You (the customer).

Q4: Why does AWS secure managed service components more than self-service components?

A: Because customers can’t configure certain parts in managed services, so AWS must secure them.

Q5: If you install software on a rented server, who is responsible for patching/configuring that software securely?

A: You.
