32 — How Policies & Permissions Are Evaluated 🧾✅❌

Reviewer / Study Guide (single-column, A4 print-ready)

🎯 Lecture Goal

Understand how AWS combines multiple IAM policies, what happens when policies “clash,” and when AWS evaluates permissions (under the hood).

Big idea ✅ An identity’s final permissions are the combination of all attached policies—but Explicit Deny always wins.

🧠 Start Here: Default Deny

By default, no permissions are granted to any identity (users, user groups, roles). You grant permissions by attaching policies.

Exam phrase ⚠️ “By default, everything is denied unless explicitly allowed.”

🧩 How Policies Are Combined

A user can have multiple sources of policies:

  • Policies attached directly to the user
  • Policies attached to groups the user belongs to (a user can be in multiple groups)

Result ✅ The user effectively gets the union of all permissions across all those policies—unless an explicit deny applies.

✅ Scenario 1: No Clash (Policies Add Permissions)

If one policy grants permissions the other policy doesn’t, they simply combine.

Example (EC2 Read + EC2 Write)

  • Policy A: allows read/inspect EC2 (view instances)
  • Policy B: allows write/change EC2 (start/stop instances)

Final result: the identity can do both read and write (effectively full EC2 access).

❌ Scenario 2: Clash (Explicit Deny Wins)

If one policy allows something and another policy explicitly denies it, AWS will deny it.

Rule to memorize ⚠️ Explicit Deny overrides Explicit Allow. Deny always wins.

Example

  • Policy A: allows reading EC2
  • Policy B: explicitly denies all EC2 access

Final result: EC2 access is denied, even though an allow exists.

⏱️ When Permissions Are Evaluated

AWS evaluates permissions at the moment an identity sends a request/command (via Console, CLI, SDK, etc.).

Step-by-step (from the lecture)

  1. 1) An identity (user/role) tries to do something (e.g., list EC2 instances)
  2. 2) That action triggers a command/request to AWS
  3. 3) AWS checks the identity’s attached policies at that moment
  4. 4) If the action is allowed → request runs ✅
  5. 5) If the action is not allowed (or is explicitly denied) → request is blocked ❌

Practical takeaway ✅ If you get “AccessDenied” errors, it means the required permission was not granted (or a deny overrides it).

🧠 One-Page Summary (Exam-Ready)

  1. 1) Default = no permissions (implicit deny) 🚫
  2. 2) Permissions come from attached policies (user + group policies) 🧾
  3. 3) Policies combine (permissions add up) ✅
  4. 4) If there’s a conflict: Explicit Deny wins ❌
  5. 5) AWS evaluates permissions when a request/command is made ⏱️

🗂️ Key Terms (Exam Focus)

Policy Permission Default deny Explicit allow Explicit deny Deny overrides allow Evaluation at request time

✅ Quick Self-Check

Answer these without looking 👀

  • What happens if multiple policies grant different permissions?
  • What happens if one policy allows and another explicitly denies the same action?
  • When does AWS check permissions—before or during the request?

Expected answers ✅ Permissions combine • Deny wins • AWS checks at request/command time.
