29 — Understanding IAM: Users, User Groups & Roles 🧑‍💼👥🎭

Reviewer / Study Guide (single-column, A4 print-ready)

🎯 Lecture Goal

Understand what the IAM service is for and learn the core IAM building blocks you will see everywhere in AWS:

  • Identities (the “who”) → Users, User Groups, Roles
  • Permissions (the “what”) → what an identity can do
  • Policies (how permissions are defined) → the rules attached to identities

Big idea ✅ IAM = Identity and Access Management → manage who can do what in your AWS account.

🧠 Key Concepts: Identities, Permissions, Policies

👤 Identities (the “who”)

Identities are entities that can perform actions in an AWS account.

  • User
  • User group
  • Role

✅ Permissions (the “what”)

Permissions define what actions an identity is allowed to perform (and on which resources).

📜 Policies (the “rules”)

Policies are the mechanism used to assign permissions. You define permissions through policies and attach them to identities.

Straightforward summary ✅ Identity = who • Permission = what • Policy = rules that grant permissions.

👤 IAM Users

Users are identities you create in an AWS account—typically for real human people who need access.

Typical use case

  • 👥 You have multiple colleagues who need to access the same AWS account
  • ✅ Create multiple IAM users (one per person)
  • 🔒 Attach permissions that control what each user can do

Important ✅ In IAM, new identities (like users) usually start with no permissions until you explicitly grant permissions (as noted in the lecture).

👥 IAM User Groups

User groups help you manage permissions for multiple users more efficiently.

Why groups exist

  • Many users need the same permissions (e.g., “Developers”)
  • Instead of copying permissions to every user, you set permissions on the group
  • Any user added to the group automatically gets the group’s permissions

Beginner-friendly analogy ✅ A user group is like a “job role in a company” (e.g., Support, Developers). Add a person to the job group → they get the standard access for that job.

🎭 IAM Roles

Roles are identities that can be temporarily assumed. They’re commonly used for AWS services or workloads that need to access other AWS services.

Important concept from the lecture ⚠️ By default, nothing is allowed for a newly created identity (user or role). You must explicitly grant permissions.

Why roles are useful

Often, one service/workload needs to interact with another service. Example: an application running somewhere needs to read/write to another AWS service.

  • Without permissions → access fails
  • Attach a role with required permissions → access succeeds

Key idea ✅ A role is a secure way to provide permissions to services (and sometimes users) without handing out long-term credentials.

🧪 Beginner-Friendly Example: App Needs to Use Another Service

Scenario: You run an application on an AWS service and it must access another AWS service.

  1. 1) 🧱 By default, the app can’t access anything (no permissions)
  2. 2) 🎭 Create an IAM role with the required permissions
  3. 3) 🧩 Attach/assign that role to the service running the app
  4. 4) ✅ The app can now perform allowed actions (only what the role policy permits)

Exam mindset ✅ When you see “service-to-service access,” think: IAM Role.

🧠 Mini Recap (One-Liners)

Users 👤

For people. Has credentials. Gets permissions via policies (directly or via groups).

Groups 👥

Permission management for multiple users. Add user → inherits group permissions.

Roles 🎭

Temporary identity. Commonly used by AWS services/workloads to access other AWS services.

🗂️ Key Terms (Exam Focus)

IAM Identity User User Group Role Permission Policy Default Deny

✅ Quick Self-Check

Q1: What does IAM stand for?

A: Identity and Access Management.

Q2: What is an identity in AWS?

A: An entity that can do actions in an AWS account (e.g., user, group, role).

Q3: What do policies do?

A: Policies define and grant permissions (what actions are allowed).

Q4: When would you use a user group?

A: When multiple users should share the same permissions.

Q5: When would you use a role?

A: When a service/workload needs permissions to access another AWS service; roles can be temporarily assumed.
