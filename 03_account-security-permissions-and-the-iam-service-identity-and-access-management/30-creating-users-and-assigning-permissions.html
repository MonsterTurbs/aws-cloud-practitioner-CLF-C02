30 — Creating IAM Users & Assigning Permissions 🧑‍💼🔑✅

Reviewer / Study Guide (single-column, A4 print-ready)

🎯 Lecture Goal

Learn where to create IAM identities (users, groups, roles), how to create a user, and how to assign permissions using policies (or groups / copied permissions). Also understand what you get after creating a user (console sign-in link, access key + secret key).

Big idea ✅ Creating identities is only half the job—permissions define what they’re allowed to do.

🧭 Where to Create Users, Groups & Roles

You can create IAM users, groups, and roles from inside your AWS account in two common ways:

  • 🔐 Go to Security Credentials and then choose Users, User groups, or Roles (left menu)
  • 🔎 Search for the IAM service and open it (same features; you start on the IAM dashboard)

Exam note ✅ You don’t need deep console skills for the exam, but you should understand what IAM is used for and the main steps.

👤 Creating a User (High-Level Steps)

  1. 1) Click Add user ➜ give the user a name 🏷️
  2. 2) Choose the access type(s): programmatic access and/or console password access 🔑
  3. 3) Assign permissions (via group / copy / attach policies) ✅
  4. 4) Optional: add tags 🏷️
  5. 5) Review settings ➜ Create user 🎉

🔑 Access Types: Console vs Programmatic

When creating a user, you can decide which access methods are available to that user.

🖥️ Password (Console) Access

If enabled, the user can sign in to the AWS Management Console via username/password.

Use this when a human will work in the web UI.

🧩 Programmatic Access

If enabled, the user can use the AWS CLI and AWS SDKs (and technically send direct API requests).

Use this for CLI/automation/scripts or app integrations that need keys.

Rule ✅ Console only → management console • Programmatic only → CLI/SDK • Both → all methods

🧠 Beginner-friendly example

  • 👩‍💻 A developer who automates deployments → needs programmatic access
  • 🧑‍💼 A manager who checks settings in the UI → needs console access
  • ✅ Some people need both

✅ Assigning Permissions (Most Important Part)

After choosing access types, you must assign permissions. The lecture lists three approaches:

1) Add to a group 👥

If you already have a user group with the right permissions, add the user to the group.

2) Copy from an existing user 🧬

Useful if you already have a user configured correctly and want to match their permissions.

3) Attach policies directly 📜

If there’s no group yet, attach one or more policies to the user.

Important concept ⚠️ IAM follows a “default deny” mindset: a new identity can’t do anything until permissions are granted (as described in earlier IAM lecture).

📜 Policies (Built-in & Custom)

Policies are documents that group permissions together. AWS provides many pre-built policies, and you can also create custom policies (more advanced).

Example: Searching policies by service 🔎

If you search for EC2, you’ll find policies related to EC2. Example mentioned in the lecture: an EC2 read-only policy lets you view/inspect EC2 resources but not modify them.

Policy “behind the scenes” (JSON)

You can view the policy JSON. It contains statements like “allow actions that start with Describe*” for EC2. You don’t need to write policies for the exam, but understanding that policies map to allowed API actions is helpful.

Key point ✅ The Management Console, CLI, and SDK all end up calling AWS APIs. Policies control which API actions are allowed.

🧨 Admin Access Policy (Important Note)

The lecture demonstrates attaching AdministratorAccess (full access to almost all AWS services) for a demo user.

Side note from lecture ⚠️ Administrator access generally does not include billing permissions by default. Billing access requires an additional policy.

Best practice ✅ Even if a user needs admin-level permissions, AWS recommends you still use an IAM user day-to-day instead of the root account.

🏷️ Tags (Optional)

You can add tags while creating the user. Tags help identify resources (and can show up in billing reports for billable resources).

Beginner note 💡

IAM users themselves typically don’t cost money, but tagging is widely useful across AWS resources.

📦 What You Get After Creating the User

After the user is created, the summary screen typically shows:

  • 🔗 A sign-in link for the IAM user (to log into this account without using root credentials)
  • 🔑 An Access Key ID and a Secret Access Key (for CLI/SDK programmatic access)

Important ⚠️ You can only view the Secret Access Key once at creation time. If you lose it, you must create a new access key pair.

Remember ✅ Access Key + Secret Key are used to sign/authorize requests made via the CLI/SDK (i.e., programmatic access).

🧠 Exam-Focused Summary

  1. 1) IAM is used to create identities: users, groups, roles 🧑‍💼
  2. 2) Users can have console access and/or programmatic access 🔑
  3. 3) Permissions are granted via policies (directly) or via groups ✅
  4. 4) Programmatic access requires Access Key + Secret Access Key 🧩
  5. 5) Best practice: use IAM users, avoid using root for daily work 🔐

✅ Quick Self-Check

Q1: Where can you create IAM users/groups/roles?

A: Via the IAM service (or via Security Credentials links that take you to the same IAM pages).

Q2: What does “programmatic access” enable?

A: Using the AWS CLI and AWS SDKs (and indirectly calling AWS APIs).

Q3: If you enable only console access, what can the user do?

A: Use the AWS Management Console, but not the CLI/SDK (no access keys).

Q4: How can you assign permissions during user creation?

A: Add to a group, copy from an existing user, or attach policies directly.

Q5: Why should you save the secret access key at creation time?

A: Because you can only view it once; if lost, you must create a new access key.

Q6: Does AdministratorAccess include billing access by default (as mentioned in the lecture)?

A: No. Billing permissions require an additional policy.
