📊 AWS CLF-C02 Study Guide — Data Analytics: Typical Tasks & Problems

Beginner-friendly reviewer on what “data analytics / data science” means in AWS contexts, common data sources, ingestion frequency, and why streaming requires special handling (Kinesis).

🎯 Learning goals

  • Understand what “data analytics” is in practical terms (why businesses care).
  • Identify common data sources (apps, scripts, devices/sensors, manual entry).
  • Explain why ingestion frequency matters (slow vs moderate vs high/streaming).
  • Know the typical AWS direction for ingestion: S3/RDS/DynamoDB for common workloads and Kinesis for streaming data.

1) 🧩 What is data analytics (and data science) in this course?

In this section, “data analytics” and “data science” are treated as closely related. In practice, they both focus on using data to make better decisions and build better products. Modern businesses generate lots of data—especially online businesses—but even traditional companies collect data via IT systems, devices, and sensors.

✅ Why it matters: Efficiently structuring and analyzing data can be a competitive advantage because it helps you understand customers, detect issues, measure performance, and improve products.

2) 🗂️ Common data sources

Before you can analyze data, you must first ingest it (get it into the cloud). Typical sources include:

🛒 A) Application data (web/mobile/desktop apps)

  • Online shop: orders, user profiles, clicks, browsing behavior, logs.
  • Apps: usage analytics, error logs, feature adoption metrics.

Example: A user places an order → your backend stores order details in a database.

🕷️ B) Crawlers, scripts, and scheduled tasks

  • Website crawlers that collect public data.
  • Scheduled tasks fetching weather data every hour/day.

Example: Every hour, a script fetches weather data → stores results for later analysis.

🚗 C) Devices and sensors (IoT-style data)

  • Cars sending telemetry data (location, engine metrics, sensor readings).
  • Industrial sensors reporting temperature, vibration, or pressure.

Example: 1,000 vehicles sending readings multiple times per second → continuous stream of events.

🧾 D) Manual data entry

  • Employees entering accounting or inventory data.
  • Customers filling forms (support tickets, onboarding, documents).

Example: Staff updates inventory in a UI → backend saves to a database.

3) ⏱️ Why ingestion frequency matters

Data sources produce data at different speeds (frequency). This matters because high-frequency data can overwhelm systems if the ingestion pipeline isn’t designed for it.

⚠️ Core risk: If too much data arrives at once and your system can’t keep up, servers may slow down, crash, or start dropping data.

🐢 Slow / low-frequency ingestion

  • Manual data entry
  • Scheduled scripts (e.g., weather data hourly)

Typical handling: Standard storage + normal request/response patterns are usually enough.

🚶 Moderate-frequency ingestion

  • Orders from an online shop
  • Typical app events (depending on scale)

Typical handling: Store into databases / object storage as events come in; scale when needed.

🏎️ High-frequency ingestion (streaming)

  • Website logs at high volume
  • Sensor / device telemetry (dozens/hundreds/thousands per second)

Typical handling: Use a streaming-capable ingestion layer designed for continuous event flow. In AWS, a key service here is Kinesis.

4) 🧰 How AWS helps with ingestion (big picture)

For many “normal” ingestion cases (apps, scripts, manual entry), you often store data in: S3 (files/objects), RDS (relational databases), or DynamoDB (NoSQL).

📦 Common AWS ingestion patterns (from the lecture)

  • 📁 S3 for file uploads (documents, images, exports).
  • 🗄️ RDS for structured relational data (orders, transactions).
  • ⚡ DynamoDB for scalable NoSQL data (high-throughput key/value access).
  • 🧰 AWS Batch for scheduled scripts/utilities that run as batch jobs.
  • 🌐 An API/backend typically receives manual entry (web/app) and stores it in S3/RDS/DynamoDB.

🌊 Streaming ingestion: where Kinesis fits

When you have an “endless stream” of data (high frequency), the lecture points to Amazon Kinesis as the key ingestion service. The core idea is that Kinesis helps ingest, handle, and process large volumes of streaming events reliably.

Exam mindset: If the scenario says “lots of events per second” or “continuous stream,” think Kinesis.

✅ Self-check (quick exam-style review)

  1. Why is data ingestion the first step in analytics?
    Because you can’t analyze data until it exists in a place where you can store and process it.
  2. Give 3 common data sources mentioned.
    Apps (web/mobile), scripts/crawlers, devices/sensors, manual entry.
  3. Why does ingestion frequency matter?
    High-frequency data can overwhelm systems if they’re not designed for it.
  4. What AWS service is highlighted for streaming data ingestion?
    Kinesis.
  5. For typical app data or file uploads, which storage services are commonly used?
    S3 for files; RDS/DynamoDB for database-style storage.
📌 Key takeaway: Most analytics pipelines start by getting data into AWS. “Normal” workloads often land in S3/RDS/DynamoDB, while high-frequency “streaming” workloads commonly start with Kinesis.

🧾 Mini glossary

  • Ingestion: Getting data into the cloud so it can be stored/processed.
  • Streaming data: A continuous flow of events (often high frequency).
  • Competitive advantage: Better decisions and product improvements derived from data insights.
