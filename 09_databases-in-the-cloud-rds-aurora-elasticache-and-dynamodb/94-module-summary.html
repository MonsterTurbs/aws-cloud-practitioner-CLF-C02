Databases in the Cloud — Module Summary (Reviewer)

Beginner-friendly notes for AWS CLF-C02: database options, when to use which service, and exam cues.

📌 Topic: Databases 🧠 Focus: Concepts & comparisons 🖨️ A4 Print: Single-column

1) Big Picture: What you learned ✅

AWS gives you multiple database services because different applications have different needs. Sometimes you want strict tables and SQL; sometimes you want flexible NoSQL; sometimes you want a super-fast cache.

Core idea: There is no “best database.” You choose based on workload, data shape, performance, and operations effort.

2) Hosting Options: Self-managed vs Managed 🧰

🛠️ Self-host on EC2

You install everything yourself (MySQL, PostgreSQL, etc.).

  • ✅ Full control (configs, plugins, OS-level tuning)
  • ⚠️ Full responsibility: backups, patching, monitoring, failover
  • Example: “We already run MySQL on servers; we want the same approach in AWS.”
🤝 Managed services

AWS does the heavy lifting for common operational tasks.

  • ✅ Easier operations: built-in backups, patching options, monitoring
  • ✅ High availability features (replication, Multi-AZ options depending on service)
  • ⚠️ Less OS-level control (you configure the service, not the underlying host)
Exam cue 🎯

If the question emphasizes “AWS manages it for you” (patching/backups/replication), think managed services (RDS/Aurora, DynamoDB, ElastiCache).

3) Key Managed Database Services to Know 🧩

3.1 RDS (Relational Database Service) — SQL 🧾

  • Managed relational databases (SQL engines like MySQL, PostgreSQL, etc.).
  • You pick: engine + version + instance class (hardware) + storage + VPC/subnets + security groups.
  • Built-in options for backups, encryption, monitoring, and high availability features.
💡 Beginner example

You are building an online shop and need tables like Users, Orders, Products. SQL + relationships are useful → RDS is a common fit.

3.2 Aurora — Amazon-built SQL engine 🚀

  • AWS-managed engine that is compatible with MySQL/PostgreSQL.
  • Designed for scalability and performance (details vary by workload).
  • Aurora Serverless: pay more “by usage” (good for unpredictable or infrequent DB activity).
  • Note: Aurora is commonly not free tier, so be mindful when experimenting.

3.3 ElastiCache — In-memory cache ⚡

  • Managed caching layer (commonly Redis or Memcached).
  • Goal: speed up reads by keeping frequently requested data in memory.
  • Often paired with a main database (e.g., RDS) to reduce DB load.
🧠 Beginner example

“Product details page is slow because everyone requests the same product data.” Cache it in ElastiCache so most requests don’t hit the main DB.

4) DynamoDB — Managed NoSQL Key-Value 📦

DynamoDB is a fully managed NoSQL database built for AWS. It is commonly used for high-performance access patterns where a strict relational schema is not required.

  • You create tables (not “database instances” that you manage).
  • Each item is identified by a Partition Key (primary identifier).
  • Capacity choices: Provisioned (plan reads/writes) or On-Demand (pay per use).
  • Access typically via AWS API/SDK/CLI (not a universal SQL interface).
Quick memory hook 🧠: RDS/Aurora = “SQL + instances”, DynamoDB = “NoSQL + tables”.

Helpful DynamoDB features (high level) ✨

  • 🌍 Global Tables: replicate tables across regions (availability + latency improvements).
  • 📣 Streams: get a stream of item changes for event-driven workflows.
  • ⚡ DAX: in-memory acceleration layer for even lower latency (extra cost).

5) VPC Placement Pattern: Web Server + Database 🧱

A very common AWS architecture pattern is:

  • 🌐 Public subnet: web server (EC2) receives traffic from the internet.
  • 🔒 Private subnet: database (RDS/Aurora or self-managed) is not directly reachable from the internet.
  • 🔐 Communication happens via private IP/DNS inside the VPC, controlled by security groups.
Exam cue 🎯

If a question says “DB should NOT be publicly accessible,” think private subnet + tight security groups.

6) Quick Comparison Cheatsheet 🧾

🧾 RDS / Aurora
  • Type: SQL / relational
  • When: tables, relationships, transactions
  • Access: SQL over network endpoint
  • Ops: managed backups/patching options
⚡ ElastiCache
  • Type: in-memory cache
  • When: need faster reads / reduce DB load
  • Access: cache commands (Redis/Memcached)
  • Ops: managed cluster options
📦 DynamoDB
  • Type: NoSQL key-value / document-ish items
  • When: flexible schema, high throughput, predictable key access
  • Access: AWS API/SDK/CLI
  • Ops: table-focused, capacity-based billing

7) Mini Practice (Quick Self-Test) 📝

  1. Which service is the best fit for a traditional SQL database with tables and joins?
  2. Which service should you add to speed up frequent reads of the same data?
  3. Which service is table-based and uses a partition key to identify items?
  4. Where do you typically place databases in a secure VPC setup: public or private subnet?
  • ✅ Answers
    1. RDS (or Aurora)
    2. ElastiCache
    3. DynamoDB
    4. Private subnet (typically)

8) Quick Exam Keywords to Watch 🔎

  • “Managed relational database” → 🧾 RDS / 🚀 Aurora
  • “Serverless relational database” → 🚀 Aurora Serverless
  • “In-memory cache” / “reduce DB load” → ⚡ ElastiCache
  • “NoSQL key-value” / “partition key” / “tables only” → 📦 DynamoDB
  • “Database should not be reachable from the internet” → 🔒 Private subnet + security groups

9) Takeaway ✅

AWS supports many database types. For the exam, focus on when to use RDS/Aurora, DynamoDB, and ElastiCache, and remember the common secure VPC pattern (public web tier, private database tier).

Tip: If you can explain the “why” in one sentence, you are ready for most CLF-C02 questions.
