Beginner-friendly notes based on the lecture transcript: why DynamoDB exists, how tables work, and how pricing & access differ from SQL databases.

1) Big idea: When would you use a NoSQL database? 🤔

Relational databases (SQL) are great when you want a strict schema and data spread across multiple related tables. But sometimes you don’t want that structure.

✅ DynamoDB is useful when:

  • 🧱 You don’t want a strict schema (records can have different “shapes”).
  • 🗂️ You don’t want to split data across many tables (you prefer fewer, wider tables).
  • ⚡ You want strong performance at scale when used correctly.

Note: “Schema-less” doesn’t mean “no planning” — it means you’re not forced into rigid table definitions like in SQL.

2) What is DynamoDB? 🧾

  • 🏁 Fully managed NoSQL key-value database service.
  • 🏗️ Like Aurora, it’s built by Amazon for AWS (cloud-native engine).
  • 🧰 You work primarily with tables (not “databases” you manage yourself).

Core mental model: In DynamoDB, you typically do not create a database server. You create tables, and AWS manages the underlying infrastructure behind the scenes.

3) DynamoDB structure: Tables → Items → Attributes 🧩

📦 Table
A collection of records (similar to a table in SQL).
🧾 Item
A single record/row in the table.
🏷️ Attributes
Fields/columns inside an item (items can have different attributes).

Keys (how items are identified) 🔑

When creating a table, you choose the key(s) used to identify entries. Think of it like: “How do I uniquely find this item?”

Beginner example (key-value idea):

  • Key: userId → Value: user data (name, email, preferences, etc.)
  • Different users can have different optional fields (e.g., middleName exists for some users, not for others).

4) DynamoDB vs SQL: What feels different? ⚖️

  • 🏛️ SQL databases: you connect, then create databases + tables, and query with SQL.
  • 🧱 DynamoDB: you create tables directly in AWS. No “database server” you manage.
  • 🧠 Data modeling: fewer tables, more flexible item shapes (can be “chaotic” at first, but common and powerful).

Exam cue ✅: If a question hints at “NoSQL / key-value / schema-less / fully managed,” DynamoDB is a prime candidate.

5) Pricing & capacity modes 💸

DynamoDB doesn’t run a visible database instance “all the time” like a classic server. Instead, you pay based on how you choose to handle read/write capacity.

📈 Provisioned capacity
You estimate expected read/write capacity in advance. Can save money if your usage is predictable.
🧾 On-demand
You pay for actual reads/writes as they happen. Great flexibility when usage is unpredictable or low.

Simple rule of thumb 🧠:

  • Predictable workload → consider Provisioned (often cheaper).
  • Spiky/unpredictable workload → consider On-demand (less planning, pay per use).

6) Security & encryption 🔒

  • 🔐 You can choose encryption settings per table.
  • 🛡️ AWS manages the underlying database operations (hardware, much of the maintenance complexity, etc.).

The transcript emphasizes: you focus on table configuration instead of database server administration.

7) How do you read/write data? 🧰

DynamoDB is AWS-native: you typically interact with it using AWS tooling.

  • 🧑‍💻 AWS SDKs (in your code)
  • 🧾 AWS CLI
  • 🌐 AWS APIs
  • 🖥️ AWS Console (for manual testing)

Key difference vs SQL ✅: You’re not using a general SQL query language. You’re using AWS tooling to read/write items in tables.

8) Beginner-friendly example: “User profiles” table 👤

Imagine a mobile app with user profiles. In SQL, you might split data into multiple tables. In DynamoDB, you might keep it simple with fewer tables.

Example items (same table, different shapes):

  • 🧾 User A: { userId: "u-101", name: "Ana", email: "ana@...", plan: "free" }
  • 🧾 User B: { userId: "u-102", name: "Ben", email: "ben@...", plan: "pro", company: "ABC Corp" }

Same table, but items can store different attributes as needed.

9) Quick exam-ready summary ✅

  • 🗃️ DynamoDB = fully managed NoSQL key-value database.
  • 🧱 Flexible structure: items can have different fields (schema-less feel).
  • 📦 You create and work with tables directly (AWS manages databases behind the scenes).
  • 💸 Capacity/pricing: Provisioned (estimate) vs On-demand (pay per use).
  • 🔒 Table-level encryption options exist.
  • 🧰 Access via AWS tools (SDK/CLI/API), not a generic SQL query language.
