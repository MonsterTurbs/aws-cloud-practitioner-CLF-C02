Single-column, print-friendly study guide based on the lecture transcript. Focus: database options on AWS (managed vs self-managed, SQL vs NoSQL, RDS/Aurora/DynamoDB).

📄 A4-ready 🧠 Beginner-friendly ✅ Exam-oriented highlights

1) What this module is about (in plain words) 🧭

In the previous section, you learned how to store files using S3. In this section, we switch from file storage to data storage using databases. Most real applications need databases to store and retrieve data like: users, products, orders, payments, etc.

📌 Big idea

Databases are typically used when you need structured data queries, fast lookups, relationships, and reliable reads/writes for your application.

2) Key choices you will learn in this section 🔎

✅ Choice A: Self-managed vs Managed databases

  • Self-managed: You run the database yourself on EC2 (you install, patch, backup, monitor, scale). 🛠️
  • Managed: AWS runs many operational tasks for you (patching, backups, monitoring, automated failover depending on service). 🧰

Exam mindset: If the question emphasizes “AWS handles maintenance/patching/backups”, that typically points to managed services.

✅ Choice B: SQL vs NoSQL databases

  • SQL (Relational): Tables, rows, columns, relationships; good for structured data and complex queries. 🧾
  • NoSQL (Non-relational): Flexible schema; commonly used for high-scale key-value/document patterns. ⚡

Tip: “SQL vs NoSQL” is about how data is modeled and queried—not just about where it’s stored.

3) Services you’ll meet: RDS, Aurora, DynamoDB 🧩

The lecture highlights that AWS gives multiple ways to run databases. At this level, the important part is recognizing which AWS service category a name belongs to.

Service What it is (simple explanation) Beginner example
RDS 🗄️ A managed relational database service. Think: AWS helps you run a SQL database without managing the OS and many routine tasks. Your app needs tables for Users, Orders, Payments and you want SQL queries like SELECT ... JOIN ....
Aurora ✨ A managed relational database engine (AWS-compatible with popular SQL engines). Often discussed as a high-performance, cloud-optimized relational option. Same use case as RDS (relational), but you want a cloud-optimized setup for demanding workloads.
DynamoDB ⚡ A managed NoSQL database service. Designed for fast key-value / document-style access patterns. You store “shopping cart by userId” and want very fast lookups: GetItem(userId).
🧠 Quick memory hook
  • RDS / Aurora = usually SQL / relational ✅
  • DynamoDB = usually NoSQL ✅

4) Beginner-friendly mental model 🧱

When you design an app, you typically pick storage based on what you need to do with the data:

  • 📦 Store files (images, PDFs, backups) → S3
  • 🗄️ Store structured business data (users, orders) → relational DB (RDS / Aurora)
  • ⚡ Fast lookups at huge scale with flexible structure → NoSQL (DynamoDB)

5) Exam-style cues to watch for 👀

  • ✅ “We want AWS to handle backups/patching/maintenance” → Managed database service
  • ✅ “We need SQL, tables, joins, relationships” → RDS / Aurora
  • ✅ “We need NoSQL, key-value, very low-latency lookups” → DynamoDB

You don’t need deep configuration details for the intro—focus on matching use case → service category.

6) Mini self-check (quick quiz) 📝

  1. 🤔 If you want to store user profile data with relationships (users ↔ orders), which category fits best?
  2. 🤔 If you want very fast lookups by a single key (e.g., sessionId), which service name should you think of?
  3. 🤔 If a question says “self-managed database”, what AWS compute service is commonly involved?
✅ Suggested answers
  1. Relational / SQL (RDS or Aurora)
  2. DynamoDB
  3. EC2 (you manage the database yourself)
