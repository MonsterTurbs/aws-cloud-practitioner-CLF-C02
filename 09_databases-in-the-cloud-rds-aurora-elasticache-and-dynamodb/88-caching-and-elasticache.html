☁️ AWS Caching & ElastiCache — Reviewer / Study Guide

Beginner-friendly notes for CLF-C02: what caching is, why it matters, and how AWS ElastiCache fits with VPC networking.

🧠 Topic: Caching Databases ⚡ Service: ElastiCache 🧰 Engines: Redis / Memcached 🕸️ Runs in: VPC + Subnets + Security Groups
Core idea (exam-level): Caching stores frequently requested data in memory so it can be retrieved faster than repeatedly querying a “regular” database (which usually hits disk under the hood). ⚡🙂

1) What is caching?

Caching means keeping a copy of frequently used data in a super-fast place (RAM / memory) so the next request can be answered quickly. 🏎️

Why is it faster?

  • 🧠 Memory access is typically faster than disk/file-system access.
  • 📉 Fewer calls to your primary database reduces load and improves overall performance.
  • 🙂 Users see faster page loads / API responses, especially during spikes.
Important: Cached data must stay “fresh enough.” If the underlying data changes (e.g., product price updated), the cache should be updated/invalidated so users don’t see stale results. 🔄

2) What is AWS ElastiCache?

Amazon ElastiCache is a fully managed in-memory caching service. It helps you create and operate a cache without managing servers yourself. 🛠️✅

What “managed” typically means (high level)

  • 📌 You choose the engine, size, networking, and some policies.
  • 🧰 AWS handles much of the operational work (service plumbing, managed deployment, etc.).
  • 📊 You can add monitoring/maintenance settings for visibility and stability.

3) Common use case example (online shop)

User 🧑‍💻 → Web/App Server (EC2) 🖥️ → Cache (ElastiCache) ⚡ → Database (RDS) 🗄️ 1) Request product details 2) App checks cache first ("Do I already have this?") 3a) Cache HIT ✅ → return data fast 3b) Cache MISS ❌ → query DB → store result in cache → return data When data changes: invalidate/update cache 🔄
  • ✅ Many users viewing the same product benefit from cache hits.
  • 📉 Database load decreases because repeated reads can come from cache.
  • 🔄 When product data updates, you refresh the cached entry.

4) ElastiCache engines: Redis vs Memcached

When creating ElastiCache, you choose an engine. The transcript highlights two typical options: Redis and Memcached. 🧩

Engine What to remember Simple mental model
Redis 🟥 Common ElastiCache engine option; supports more advanced patterns in many real-world architectures. "Feature-rich cache" (often used when you need more than basic caching)
Memcached 🟦 Common ElastiCache engine option; typically used for straightforward caching scenarios. "Simple, lightweight cache"

Exam approach: If a question mentions ElastiCache, think: “managed in-memory cache,” typically Redis/Memcached, used to speed up frequent reads. ⚡

5) Scaling concepts: cluster mode, shards, replicas

Cluster mode (high-level)

Cluster mode is a way to scale the cache by using multiple connected nodes (often described as shards that split the data). 🧱🧱🧱

  • 📈 Can help with availability and performance (depending on design).
  • 🧩 Instead of one cache node, you can have multiple pieces working together.
Quick definitions:
  • Node type = the hardware profile for cache nodes (similar idea to instance types). 🧰
  • Replica = an additional copy/node to improve availability and sometimes read capacity. 🧯
  • Multi-AZ = run across multiple Availability Zones for resilience. 🏢🏢

6) Networking: VPC, subnets, security groups

ElastiCache is created inside a VPC, just like RDS in the previous lesson. 🌐

  • 🕸️ Choose the VPC where the cache should live.
  • 🏷️ Choose subnets (often via a subnet group) that the cache can use.
  • 🧱 Attach security groups to control who can connect and on which ports.
Security reminder: Just like databases, caches should usually not be public-facing. Typically, your app (EC2/Lambda/etc.) talks to the cache privately inside the VPC. 🔒

7) Operations: encryption, backups, maintenance, monitoring

The transcript highlights that you can configure operational settings to match your needs. 🛡️📊

🔐 Encryption

  • Protects sensitive cached data (where applicable).
  • Useful for compliance or security requirements.

💾 Backups

  • Helpful if you need recovery options (depending on engine/setup).
  • Commonly paired with maintenance strategies.

🧰 Maintenance

  • Settings for upgrades/patching windows.
  • Helps reduce unexpected disruptions.

📈 Monitoring

  • Visibility into cache health and performance.
  • Useful for troubleshooting and capacity planning.

8) Console path (what you’d click in AWS)

  • 🔎 Search for ElastiCache in the AWS Console.
  • ➕ Create a Redis or Memcached cluster.
  • ⚙️ Choose: cluster mode, engine version, node type, Multi-AZ, replicas, port.
  • 🕸️ Choose: VPC + subnets + security group.
  • 🛡️ Optional: encryption, backups, maintenance, monitoring.

💸 Cost note: Like most databases, ElastiCache generally costs money; free-tier eligible options may exist. Always check current pricing and quotas.
