☁️ AWS CLF-C02 Reviewer — CodeBuild & CodeArtifact

Topic: Developer tools for testing/building code and managing packages (artifacts) in AWS.

🧠 Beginner-friendly 🧾 Print-optimized (A4) 📄 Single-column layout 🎯 Exam-focused takeaways
Big idea 💡
In a typical development workflow, you write code → store it in a repo → test & build → deploy.
CodeBuild helps with the test & build step, while CodeArtifact helps you store and control packages your builds depend on.

1) Where CodeBuild fits in the workflow 🧩

CodeBuild provides a managed build environment (like a temporary “build server”) where AWS runs your commands to:

  • 🧪 Run tests (unit tests, integration tests, linting)
  • 🏗️ Build your app (compile, bundle, package, create Docker image, etc.)

Key point: you don’t manually create or manage an EC2 build server. AWS manages the underlying servers for you.

2) CodeBuild basics (what you configure) ⚙️

📦 Code source Where the code comes from (e.g., CodeCommit, GitHub, other supported sources). This is what CodeBuild downloads before running build steps.
🖥️ Build environment You choose OS/runtime image presets (with common tools preinstalled). You can also add environment variables.
⏱️ Timeouts Helps avoid paying for “stuck” builds. If the build exceeds the timeout, it stops automatically.
🧾 BuildSpec file A file that lists the commands to run (install deps → test → build). This is the “recipe” for your build.
📤 Build output If your build produces an artifact (zip/package/compiled output), you can store it (commonly in S3) for deployment later.
🔔 Triggers Builds can run manually or automatically (e.g., when code changes happen).

3) BuildSpec (simple example) 🧾

The BuildSpec file tells CodeBuild exactly what to do. Think of it like a checklist of commands. A typical pattern is: install dependencies → run tests → build output. 

# Example (conceptual) buildspec.yml
version: 0.2

phases:
  install:
    commands:
      - echo "Install dependencies"
      - npm ci
  build:
    commands:
      - echo "Run tests"
      - npm test
      - echo "Build app"
      - npm run build

artifacts:
  files:
    - '**/*'
  base-directory: dist

Beginner tip 👶

If you are only running tests, you might not produce any build artifacts. If you are building, you typically produce something like a ZIP, binary, or compiled output.

4) CodeArtifact (why it exists) 📦

Most projects depend on third‑party libraries (packages) so you don’t reinvent the wheel. Normally, you download these from public package registries.

CodeArtifact provides a managed repository where you can:

  • 🌍 Use public packages (via mirroring/proxying) so builds are faster/more controlled
  • 🔒 Publish private internal packages (company-only libraries)
  • 🧩 Centralize dependency management in AWS

CodeArtifact is optional—use it if you want more control, performance, or private package hosting.

Quick analogy 🧠
If CodeBuild is the “kitchen” where you cook (build) your app, then CodeArtifact is your “pantry” where you store ingredients (packages) — including private ingredients your team doesn’t want to publish publicly.

5) CodeBuild vs CodeArtifact (exam-friendly comparison) 📝

CodeBuild 🏗️ Runs tests and build commands in a managed environment. Produces build output (artifacts) you can store.
CodeArtifact 📦 Stores and manages packages/dependencies (public + private). Helps your builds get dependencies reliably.

6) Practical mini-scenario (easy to imagine) 🧪

Scenario: You have a Node.js app.

  • 📁 Code is stored in Git (CodeCommit or GitHub).
  • 🧪 On every push, CodeBuild runs npm test and then npm run build.
  • 📤 The build output is uploaded to S3.
  • 📦 Dependencies come from npm. If you want tighter control, you can route dependencies through CodeArtifact.

This matches the transcript idea: CodeBuild executes your workflow steps, CodeArtifact is an optional package repository to support builds.

7) Quick Check ✅ (self-test)

Q1: What problem does CodeBuild solve?

✅ It provides a managed environment to run tests and build your code using commands defined in a BuildSpec.

Q2: Do you need to create EC2 instances to use CodeBuild?

✅ No. You configure the environment, but AWS manages the underlying servers.

Q3: What is a BuildSpec file?

✅ A file that defines the steps/commands (install → test → build) that run during the build.

Q4: What problem does CodeArtifact solve?

✅ It provides a managed package repository so you can use public packages via a controlled source and publish private internal packages.

Q5: When is CodeArtifact most useful?

✅ When you need private packages, better dependency control, and/or more reliable/faster dependency retrieval.

8) Mini-glossary 📚

  • 🧪 Test: Checking if code works correctly (unit/integration tests, linting).
  • 🏗️ Build: Creating deployable output (bundle, binary, Docker image, ZIP, etc.).
  • 🧾 BuildSpec: The “recipe” of commands CodeBuild runs.
  • 📦 Package: Reusable library/dependency (public or private).
  • 📤 Artifact: Output produced by a build (e.g., ZIP file, compiled output).

Key takeaways 🎯

  • 🏗️ CodeBuild = managed environment to run tests + builds using a BuildSpec.
  • 📦 CodeArtifact = managed package repository (public + private) to support builds.
  • 🧠 Exam mindset: know the “role” each service plays in the developer workflow.
