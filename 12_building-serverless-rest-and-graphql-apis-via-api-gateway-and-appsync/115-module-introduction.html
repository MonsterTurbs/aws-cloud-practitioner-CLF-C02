🌐 Why do we need APIs for web & mobile apps?

A web or mobile app usually needs data and business logic that should not live purely on the user’s device. For example: saving a profile, checking an order, uploading a photo, or logging in.

An API (Application Programming Interface) is a controlled way for an app to talk to your backend code. Typically, the app sends an HTTP request to an endpoint, and the backend returns a response.

💡 Beginner-friendly mental model

Think of an API like a restaurant menu: the menu shows what you can order (allowed requests), and the kitchen (backend code) prepares the result. Users should not walk into the kitchen directly.

🧪 Simple example

Mobile App  →  HTTPS Request  →  API Endpoint  →  Cloud Code  →  Database
  • 📲 App sends: POST /login with email + password
  • ☁️ Cloud code validates credentials
  • 🔐 Cloud returns a token (so user stays logged in)

🧱 REST vs GraphQL (high-level)

🔷 REST API (common, resource-based)

  • REST uses multiple URLs (“endpoints”) for resources.
  • Typical operations: GET, POST, PUT, DELETE.
  • Example: GET /products, GET /products/123.
GET /products/123
→ returns the product details for ID 123

🟣 GraphQL API (query-based)

  • GraphQL often uses a single endpoint (conceptually) and lets the client ask for exactly the fields it needs.
  • Useful when different screens need different shapes of data.
  • Example: ask for id and name only (not the entire product record).
query {
  product(id: "123") {
    id
    name
  }
}

Exam mindset: you mainly need to recognize that AWS supports both styles and has services that help build them.

☁️ What “serverless API” means in AWS (concept)

A serverless API typically means you can expose endpoints to users without provisioning servers. A common pattern is: 

Client (Web/Mobile)
   ↓ HTTPS
API Layer (e.g., API Gateway)
   ↓ triggers
Compute (e.g., AWS Lambda)
   ↓ reads/writes
Data Store (e.g., DynamoDB / RDS)
  • ⚡ Scales automatically (within service limits).
  • 💸 Pay-per-use is common (instead of paying for server uptime).
  • 🧩 Often combined with other services (auth, storage, database).

👤 AWS account users vs app users (very important)

Two different “user types” exist:

  • 🧑‍💼 AWS account users: admins/developers/operators who manage AWS resources (IAM users/roles).
  • 🧑‍🤝‍🧑 Application end-users: customers who use your website/mobile app (they should NOT access your AWS account).

This module focuses on building experiences for app end-users: authentication, API access, and calling cloud code.

🔐 Authentication for user-facing apps (what to expect)

User authentication means your app can verify a user’s identity (login/signup), then allow access to protected APIs. In AWS, a common service for this area is Amazon Cognito (user pools / identity pools), though the specific service details may come later in your course.

🛡️ Quick distinction

  • Authentication = “Who are you?”
  • Authorization = “What are you allowed to do?”

🧰 Using AWS services from frontend code

Your web/mobile app can interact with AWS services through the AWS SDKs or helper tooling. The key idea is: the frontend should not contain long-term secrets. Instead, it should use secure authentication flows and temporary credentials/tokens.

  • 📲 Frontend calls API endpoints over HTTPS
  • 🔑 Auth returns tokens/credentials
  • ✅ Tokens are used to access protected resources
