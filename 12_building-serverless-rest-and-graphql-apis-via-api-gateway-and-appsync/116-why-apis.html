Big Picture: Why do apps need APIs? 🌐🔌

When you build a web app (browser) or mobile app (phone), the app often needs data and actions from the cloud: product lists, user profiles, orders, image processing, and more.

That cloud logic usually lives behind a backend HTTP API. The app sends a request, the backend returns a response.

Simple mental model: App (client) ➜ HTTP API ➜ Cloud code + database ➜ Response back to the app. (The app shows the data to the user.)

Beginner example 🧠

  • 📱 Mobile app needs all products to display a shop screen.
  • ☁️ Database is in the cloud (e.g., RDS/DynamoDB). Code to fetch products runs in the cloud.
  • 🔁 App sends a request → backend fetches from DB → returns product data (usually JSON).

Two common styles of data-focused web APIs 🧭

In practice, these “data-driven APIs” are commonly built as either:

  • REST APIs 🧩 — many URLs (endpoints) that represent resources (e.g., books, products).
  • GraphQL APIs 🧠 — typically one URL (one endpoint), but the request contains a query telling the server exactly what data is needed.
Exam-friendly takeaway ✅
  • REST is extremely common.
  • GraphQL is also popular and helps request exact data (often less over-fetching).

REST API basics (easy picture) 🧱

With REST, you usually have multiple URLs, and each URL represents a resource. You use common HTTP methods (verbs) like GET, POST, PUT, DELETE to express the action.

Example: Read data

Goal: Fetch book with ID 1.

GET https://yourdomain.com/books/1

Typical result: the server returns the full “book” object (all fields it decides to return).

Example: Create data

Goal: Add a new book.

POST https://yourdomain.com/books

Body (example):
{
  "title": "Cloud Basics",
  "author": "A. Student"
}

POST requests commonly carry data in the request body (e.g., JSON).

Tip 💡 Don’t overthink the REST rules for this exam. Just remember: REST = resource URLs + HTTP methods.

GraphQL API basics (easy picture) 🧠

With GraphQL, you often send requests to one endpoint. Instead of many URLs, the request body contains a GraphQL query describing exactly what data you want.

Example: One endpoint, query controls the data

Goal: Get only the book title (and not the entire object).

POST https://yourdomain.com/graphql

Body (example):
{
  "query": "query { book(id: 1) { title } }"
}

Key idea: the client asks for specific fields, which can reduce redundancy / over-fetching.

Key takeaway: GraphQL makes it easier to request partial data in a structured way.

REST vs GraphQL (what matters for CLF-C02) ⚖️

REST 🧩
  • Multiple endpoints (URLs) for different resources.
  • Uses HTTP methods like GET/POST/etc.
  • Very common in real-world systems.
  • May return “more data than needed” depending on endpoint design.
GraphQL 🧠
  • Often a single endpoint.
  • Client sends a query specifying fields to return.
  • Can reduce over-fetching (leaner responses).
  • Also popular; choice depends on team/company preferences.
Remember ✅ Both REST and GraphQL are just “ways to design APIs”. You can implement either style using code running on EC2, containers, or Lambda.

Where AWS helps: API Gateway (preview) 🧰

You can build APIs by writing and running code yourself (EC2, containers, Lambda). But AWS also provides services to make this easier.

From the transcript’s key point: AWS offers a service that helps you build REST APIs without writing the full server from scratch — that service is Amazon API Gateway.

Practical idea: API Gateway can sit in front of your backend (often Lambda) and handle API routing. (More details come in later lessons.)

Mini glossary 📚

  • Client: The app (browser/mobile) that sends requests.
  • Backend: Cloud code/services that process requests.
  • HTTP API: A web-accessible interface using HTTP requests/responses.
  • Endpoint: A URL that receives requests (common term in REST).
  • Resource: A thing you manage via an API (e.g., book, product, order).
  • Over-fetching: Receiving more data than needed.

One-sentence summary 🎯

Web/mobile apps often need to talk to cloud code and databases via HTTP APIs, typically designed as REST or GraphQL, and AWS can simplify REST APIs with API Gateway.
