🌟 Big Idea

Cognito is AWS’s managed service for sign-up, sign-in, and user authentication for the users of your application (e.g., customers of an online shop).

It stores user credentials securely, handles validation, and can integrate with social sign-in providers. It can also help your app users obtain temporary AWS credentials when your app needs to access AWS services (e.g., upload to S3).

🆚 IAM vs Cognito (Don’t Confuse These)

👤 IAM
Users/roles for AWS account access (admins, developers, automation). Controls what can be done inside your AWS account.
🧑‍💻 Cognito
Users for your application (customers/end-users). Handles app authentication (sign-up, sign-in, MFA, etc.).

Rule of thumb: IAM = “Who can manage AWS?” • Cognito = “Who can log in to my app?”

👥 Cognito User Pools

User Pools are like an AWS-managed user directory (think: a secure database of your app users).

  • 🗄️ Stores user accounts and credentials (securely)
  • 🔑 Enforces sign-in rules (password policy, MFA, verification)
  • 📨 Handles user flows (sign-up, sign-in, password reset / recovery)
  • 🧩 Integrates with your front-end so your app can check “Is the user logged in?”

Beginner mental model 🧠

Think of a User Pool like a hosted “login system” you don’t need to build yourself.

🌐 Federated Identities (Identity Pools)

Cognito can also support third‑party sign-in (social login) through federated identity setups.

  • 🔗 Connect identity providers like Google, Facebook, Apple (and others)
  • 🧾 Users can authenticate using existing accounts instead of creating a new password
  • 🧠 Cognito can still help your app map those users to controlled AWS permissions (when needed)

Common confusion ⚠️

User Pool = your app’s native user directory (email/password etc.).
Identity Pool (federated identities) = connects authenticated users to temporary AWS credentials and can include social providers.

🪪 Temporary IAM Permissions (When App Users Need AWS Access)

Sometimes, your app user must call an AWS service directly (example: uploading a photo to S3). You don’t want to give them permanent credentials.

Instead, Cognito can help provide temporary, limited permissions (least privilege) that expire.

Security point 🔒

These permissions should be narrow (e.g., “upload only to this one S3 bucket path”), not broad admin access.

⚙️ What You Typically Configure in Cognito

  • How users sign in: email/username/phone, etc.
  • Password policy: length, complexity requirements
  • MFA: optional or required (e.g., SMS/app-based)
  • Account recovery: how password resets work (email/SMS)
  • User verification: email/phone verification flows
  • Messaging: what emails/SMS Cognito sends and how
  • Federation: which third-party providers are allowed (Google, Apple, etc.)

🧪 Beginner Examples

Example A — Online Shop Login (Email + Password) 🛒

Goal: Users create accounts and log in to see orders.

  • Use: Cognito User Pool
  • Enable: password policy + optional MFA
  • Front-end uses Cognito to sign in and to check login state
User signs up → Cognito stores credentials securely
User logs in → Cognito validates credentials
App receives authenticated session/token → App can call your API

Example B — “Login with Google” ✨

Goal: Users sign in using Google instead of a new password.

  • Use: Federated identities / identity providers
  • Cognito coordinates authentication with Google
  • Your app receives an authenticated identity and can proceed
User taps “Sign in with Google” → Google authenticates user
Cognito accepts the federated identity → App treats user as logged in

Example C — User Uploads an Image to S3 📦🖼️

Goal: After login, a user uploads files directly to S3 (fast and scalable).

  • Use: Cognito + temporary AWS permissions
  • User gets limited permission only for the needed S3 action
Authenticated user → receives temporary credentials (limited)
User uploads to S3 (allowed bucket/path only)
Credentials expire automatically

📝 CLF-C02 Exam Notes

  • ✅ Cognito is for app user authentication (your product’s users).
  • ✅ IAM is for AWS account permissions (admins/devs/automation).
  • ✅ Cognito supports user pools and federated sign-in.
  • ✅ Cognito can be used to grant temporary, scoped AWS access when needed.

✅ Quick Self-Check

1) If I need customers to log in to my mobile app, what service fits best?

➡️ Cognito (managed app user authentication).

2) If I need a developer to deploy resources and manage AWS services, what fits best?

➡️ IAM (AWS account identities and permissions).

3) If users want “Sign in with Google,” what Cognito feature is relevant?

➡️ Federated identities / identity providers (social sign-in).

Mini-summary: Cognito = login system for your app users. IAM = security and permissions for your AWS account.
